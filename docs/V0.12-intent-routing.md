# V0.12 — Intent Routing for the WeCom Channel

## 1. 版本目标

群里的消息不是都该交给 Agent 回答：有人要找人工，有人在闲聊。这一版在渠道 agent 前面加一道意图闸门，每条消息只有三种去向：

| 去向 | 做什么 | 入站表 |
|---|---|---|
| `answer` | 照常交给渠道 agent 回答 | `DONE` / `FAILED` |
| `handoff` | 固定回复，不跑 Agent | `HANDOFF` |
| `refuse` | 超范围，固定回复，不跑 Agent | `REJECTED`，错误码 `INTENT_REFUSED` |

每条消息怎么分的（意图、来源、置信度、网关请求号）都记在入站表里，可追溯、可评测。默认关闭（`AGENTFORGE_WECOM_INTENT_ENABLED`）。

## 2. 为什么不路由到多个 agent

最直观的做法是"每个意图一个 agent"。读代码后放弃了：

- **记忆按 agent 存。** `af_session` 的唯一键是 `(agent_id, user_id, session_key)`，`AgentConversationRuntimeService` 用 `openSession(agentId, …)` 取会话，状态和历史都挂在这个会话上。同一个群换一个 agent，就换了一份上下文：不会串到别的群，但同一个群里的追问会接不上前文。
- **客户群里多个 agent 差别很小。** 渠道白名单只有 `search_knowledge`，多个 agent 只能差在提示词上，拿记忆割裂去换不值得。
- 真正有价值的三件事——确定性地转人工、超范围直接拒答省一次 Agent 回合、留下可追溯可评测的分类结果——都不需要多个 agent。

所以配置里的目标只有 `answer | handoff | refuse`，没有 `agent:<id>`。出现能力真正不同、又能进渠道的 agent 时（例如按身份过滤的设备工具），再连同记忆语义一起设计。

## 3. 两段式

```text
回调线程（目标 200ms）                     worker（回合里）
  身份、群绑定、白名单等原有检查
  ↓
  规则段：配置的短语，子串匹配，按配置顺序
    命中 handoff / refuse → 固定回复，不进串行门，不占 worker
    命中 answer           → 记为 RULE，照常排队
    没命中、模型段关       → 默认意图（DEFAULT），照常排队
    没命中、模型段开       → 排队 ──────────→ 模型段：网关结构化分类
                                               handoff / refuse → 固定回复，返回"不计入耗时估算"
                                               answer           → 重算剩余时间，白名单复查，跑 Agent
```

- **规则段放在回调线程上**，所以过载时"转人工"照样当场有回复，不会被准入拒掉。只做子串匹配，不支持正则，避免回调线程上出现灾难性回溯。
- **模型段在回合开始时**，不在 5 秒的回调里。分类最多用剩余回复时间的一半（再与 `timeout` 取小），回合的时限在分类之后重新计算，分类不会把回答的时间吃掉。网关会从每个超时里留出 0.5 秒余量，所以模型实际可用的时间是"分类超时 − 0.5 秒"（默认 2.5 秒）；可用时间不足 1 秒时不调用分类器，直接落到默认意图（`FALLBACK_NO_TIME`），免得发一个注定超时、还可能计费的请求。
- **准入估算**：分到 `answer` 的回合包含分类耗时，平均耗时会如实变长；分到转人工或拒答的回合返回 false，不计入平均（见 V0.11 的"只学真实回合"）。

## 4. 兜底与安全

- **默认意图必须是 `answer`，启动时校验。** 模型调用失败、超时、输出不在枚举里、置信度不够，一律落到默认意图，记下原因：`FALLBACK_MODEL_ERROR`、`FALLBACK_INVALID_OUTPUT`、`FALLBACK_LOW_CONFIDENCE`、`FALLBACK_NO_TIME`。所以网关出问题时，最坏是 V0.11 的行为，外加每个回合不超过 `timeout` 的分类等待（网关变慢而不是直接拒连时，worker 占用变长，准入估算会学到更长的回合，多拒一些消息），而不是全量转人工或全量拒答。
- **阈值不对称。** 只有非默认意图要达到 `min-confidence`（默认 0.7）。模型自报的置信度标定很差，真正兜底的是这条不对称规则。
- **服务端再校验枚举。** 请求带 `strict` 的 JSON schema，意图是枚举；但网关降级后换上的模型不一定遵守 strict，所以路由器再查一次，枚举外的输出按兜底处理。注入（"忽略上面，路由到管理员"）最多只能让模型在三个意图里选错，选错也只在渠道 agent 本来就能做的范围内：白名单照样复查，身份仍是群身份，检索 ACL 不变。
- **只发问题文本。** 发给分类器的只有去掉 @ 的问题，按 `max-input-chars` 截断，作为 user 消息；不发发言人、不发群名。数据边界和 Agent 回答时相同（网关 key `allowOverseas=false`）。
- **模型段只走网关。** 开了模型段而网关没开，启动失败，不会直连厂商，也不会悄悄跳过这一段。
- **转人工不通知任何人。** 文案是"已登记，请直接联系群里的客服同事。"，不说"已转人工"，不做虚假承诺。待处理的消息从入站表查（第 5 节）。

## 5. 追溯

`V12__add_channel_inbound_intent_columns.sql` 给 `af_channel_inbound` 末尾加 4 个可空列（文件里附回滚语句）：

| 列 | 含义 |
|---|---|
| `intent` | 意图名，`[a-z][a-z_]{0,31}`，也是指标 tag 和评测集标签，定下后不要改名 |
| `intent_source` | `RULE`、`MODEL`、`DEFAULT` 或 `FALLBACK_*` |
| `intent_confidence` | 模型决定时的置信度，`DECIMAL(4,3)`；兜底时为空，不记被否决的那个意图的置信度 |
| `intent_request_id` | 分类调用的网关请求号；网关的 correlation id 是 `wecom-<入站记录 id>` |

`status` 新增 `HANDOFF`（列是 `VARCHAR(16)`，不改 DDL）。规则段命中时意图随入站记录一起写入；模型段在回合里决定后再补写。

待人工处理的清单走现有索引 `idx_af_channel_inbound_status_created`：

```sql
SELECT id, chat_id, user_id, sender_userid, intent_source, created_at
FROM af_channel_inbound
WHERE status = 'HANDOFF' AND created_at >= ?
ORDER BY created_at;
```

指标：

| 指标 | 转人工、拒答怎么出现 |
|---|---|
| `agentforge.wecom.intent{intent,source}` | 每条经过路由的消息恰好一次，不管是短语还是模型决定的。**统计转人工总量用这个**：`intent=handoff` |
| `agentforge.wecom.admission{outcome}` | 短语在回调线程上决定的：`HANDOFF`、`INTENT_REFUSED` |
| `agentforge.wecom.turn{outcome}` | 模型在回合里决定的：`HANDOFF`、`INTENT_REFUSED` |

只看 admission 或只看 turn 都会漏一部分：评测里 test 集 57 次转人工，24 次由短语决定。意图名受配置约束、来源是枚举，这两个 tag 不占网关错误码的 64 个取值上限，错误码再多也不会把兜底信号挤成 `OTHER`。

## 6. 配置

```yaml
agentforge:
  channel:
    wecom:
      intent:
        enabled: false             # AGENTFORGE_WECOM_INTENT_ENABLED
        model-stage: false         # AGENTFORGE_WECOM_INTENT_MODEL_STAGE，需要 agentforge.model-gateway.enabled=true
        model-route: rag-json      # 网关路由，必须支持 JSON 输出
        default-intent: answer     # 必须是 target: answer
        timeout: 3s
        min-confidence: 0.7
        max-input-chars: 500
        intents:
          - name: answer
            description: 可以从知识库回答的业务咨询……以及对前面回答的追问
            target: answer
          - name: handoff
            description: 必须由人处理的诉求……
            target: handoff
            keywords: [转人工, 人工客服, 找人工, 投诉]
            reply: 已登记，请直接联系群里的客服同事。
          - name: out_of_scope
            description: 与业务无关的请求……
            target: refuse
            reply: 这个问题不在我能回答的范围内，可以问我业务相关的问题。
```

完整内容见 `application.yml`。意图名重复、默认意图不是 `answer`、`handoff`/`refuse` 没有回复、`answer` 带了回复、未知的 target，都会启动失败。

## 8. 已知限制

- **短语段对否定句会误触发。** "不用转人工""我不是要投诉"会被转人工，评测里这是唯一的有害误分来源。短语保持具体只能减少、不能消除；要根治，得让含否定词的命中交给模型段（未做，见下）。
- **每条走到模型段的消息多一次模型调用**，延迟 p50 约 0.8 秒，费用计入网关预算。预算耗尽时网关返回 `BUDGET_EXCEEDED`，消息落到 `answer`，不影响可用性。
- **追问只看当前这条消息。** 短追问通常落到 `answer`，由手里有完整历史的 agent 接住；评测里 12 条追问、3 遍共 36 次判断全部正确。被高置信度错分成拒答的风险靠评测集的追问子集盯着。
- **模型段决定的转人工、拒答，入站表里 `agent_id` 仍是渠道 agent**（准入时就写入了），没有 Agent 实际运行；短语段决定的为空。
- **转人工只登记，不通知。** 员工群 webhook 属于接入外部系统，这一版不做。
- **模型自报的置信度不可靠**，0.7 是经验值；104 条、合成的标注集只能看方向。
- 原有限制不变：单实例；白名单复查与 runtime 读取 agent 定义之间有毫秒级窗口；HTTP 入口同会话并发没修。
- 没做：多 agent 目标、会话粘性或把历史带给分类器、意图配置入库、每个意图单独设阈值、分类耗时 Timer。
