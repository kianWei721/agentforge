# V0.9 — Model Gateway Client

## 1. 版本目标

AgentForge 的模型调用改走独立的 [model-gateway](https://github.com/kianWei721/model-gateway)。这样用量和成本可以按团队、项目归属；厂商密钥不再出现在 AgentForge 里；降级、预算和数据出境规则都在网关一处执行。

本版范围：

- 知识检索里的两次 chat-completion 调用：查询改写、可答性判定；
- 聊天接口可以选用 `gateway` provider。

不在本版：Agent runtime、embedding、rerank 仍然直连百炼，原因见第 7 节。

## 2. 开关与"不静默回退"

`agentforge.model-gateway.enabled=true` 之后：

- 改写和判定**只**走网关。它们的 base-url、api-key、model 换成网关的地址、网关 key 和 `rag-route`（`viaGateway`），原来的 `DASHSCOPE_*` 配置不再读取。
- 网关不可用时按失败处理，不会改回直连。悄悄回退的话，账单和网关流水对不上，网关的预算和出境规则也被绕过了。

启动时校验：

| 情况 | 结果 |
|---|---|
| `agentforge.model.provider=gateway`，网关没开 | 启动失败 |
| 网关开启，但缺 base-url 或 api-key | 启动失败 |

AgentForge 用的网关 key 必须 `allowOverseas=false`：判定请求里带着知识库原文。

## 3. 请求约定

| 项 | 做法 | 原因 |
|---|---|---|
| 字段 | 只发 OpenAI 标准字段；不再发 `enable_thinking` | 网关会拒绝私有字段，按模型目录的 `extra-body` 注入。降级到别家时不会带着通义的私有参数 |
| `max_tokens` | 改写 512；判定 `256 + 160 × 候选数` | 网关按 `max_tokens` 预占预算。判定输出被截断会导致 JSON 解析失败、整次检索 fail-closed，所以按候选数留余量 |
| `X-Correlation-Id` | 每次检索生成一个 `kr-<uuid>`，改写和判定共用；聊天用 `chat-<sessionId>`，不合法的会话 ID 换成随机值 | 一次检索触发的所有模型调用，可以在网关流水里一次查出 |
| `X-Gateway-Deadline-Ms` | 本地超时减 500ms | 网关比 AgentForge 先放弃，不替一个已经没人等的请求花钱 |
| 路由 | 改写和判定用 `rag-json`，聊天用 `standard` | `rag-json` 只放用这套 JSON Schema prompt 评测过的模型 |

聊天请求不发 OpenAI 的 `user` 字段：用户 ID 留在 AgentForge 内部，不交给厂商。

## 4. 失败怎么处理

重试判断看网关返回的 `error.code`，不看 HTTP 状态码。同样是 429，限流可以重试，预算用完了不行；同样是 504，没来得及调用上游可以重试，结果未知的那次厂商可能已经扣费了。规则集中在 `ModelCallFailedException.retryable`。

| 错误码 | 来源 | 可重试 |
|---|---|---|
| `RATE_LIMITED`、`NO_UPSTREAM_AVAILABLE`、`DEADLINE_EXCEEDED` | 网关 | 是 |
| `GATEWAY_UNREACHABLE` | 本地：连不上网关 | 是，请求没有发出去 |
| `BUDGET_EXCEEDED` | 网关 | 否，当天预算不会恢复 |
| `UPSTREAM_OUTCOME_UNKNOWN` | 网关 | 否，厂商可能已经扣费 |
| `GATEWAY_TIMEOUT` | 本地：等网关超时 | 否，网关可能还在调用、还在计费 |
| `GATEWAY_CONNECTION_LOST` | 本地：连接中途断开 | 否，请求可能已经发出 |
| 其余（参数、路由错误等） | 网关 | 否 |

各个调用点的处理：

- **改写失败**：退回原始 query。`reasonCode` 记网关的错误码（以前统一记 `PROVIDER_ERROR`）。
- **判定失败**：仍然 fail-closed。`search_knowledge` 工具返回 `MODEL_<code>`，`retryable` 照搬上表，`gatewayRequestId` 放在 data 里。不可重试的失败会被 Tool Governance 拦住同参数的重复调用，正好挡住"结果未知还再试一次"。
- **`POST /knowledge/search`**：可重试的返回 503，其他返回 502；响应头带 `X-Gateway-Request-Id`。
- **聊天 SSE**：发一个 `error` 事件，内容是 `{code, retryable, gatewayRequestId, message}`。

## 5. 可追溯

检索结果新增 `modelCallDiagnostics`：一个 correlationId，加上这次检索的每一次模型调用（stage、gatewayRequestId、servedProvider、servedModel、errorCode）。失败的调用也记。`/knowledge/search` 的响应和 `search_knowledge` 工具数据（`modelCorrelationId`、`modelCalls`）都带上了。

拿 correlationId 去网关查 `GET /admin/requests?correlationId=`，能看到每次尝试的成本和降级轨迹。

聊天 chunk 的 `model` 字段是实际服务的 `PROVIDER/model`，不是路由名。降级之后，用户看到的是真正回答的那个模型。

## 6. 测试覆盖

| 测试 | 证明什么 |
|---|---|
| `ModelGatewayClientTest` | 请求带 Bearer、correlation id、截止时间（超时减 500ms）；重试判断按错误码而不是状态码；连不上可重试，超时不可重试；非网关格式的错误退回 `HTTP_<status>` |
| `KnowledgeGatewayModeTest` | 改写和判定只发标准字段，`model` 是 `rag-json`，带 `max_tokens`；成功和失败的调用都记进上下文；判定失败抛出的是 `ModelCallFailedException`，不会被包成普通的状态异常；`viaGateway` 不读直连配置 |
| `HybridKnowledgeRetrieverTest.gatewayRewriteFailureShouldFallBackWithItsCodeAndShareOneCorrelationId` | 改写失败时退回原 query 并记下错误码；改写和判定共用同一个 correlation id |
| `KnowledgeSearchToolTest` | 网关错误映射成 `MODEL_<code>`，可重试性和请求 ID 照传，被包在别的异常里也能找到；成功时带上模型调用记录 |
| `GatewayModelProviderTest` | 一次性返回整段回答，`model` 是实际服务的模型；不发 `user` 字段；网关错误传到订阅方；`provider=gateway` 但网关没开时启动失败 |

假网关是 JDK `HttpServer`（`FakeGateway`），可以按需返回状态码、响应头、错误体和延迟。

## 7. 已知限制与没做的事

- **只联调过聊天路径。** 2026-10-22 的冒烟中，AgentForge 经真实网关调到了百炼，成功和失败两条路径都跑通，SSE、网关响应头、流水三方用同一个请求号和 correlation id 对得上，记录见 model-gateway 仓库的 `docs/smoke-test-2026-10-22.md`。查询改写和可答性判定经网关的调用需要 ES，没有在真实环境里跑过。
- **网关不支持流式。** `GatewayModelProvider` 一次性返回整段回答，不伪造逐字的流。
- **Agent runtime 仍然直连。** 它用的是 AgentScope 的 `DashScopeChatModel`；改走网关需要 AgentScope 的 OpenAI 兼容模型实现，本地依赖里没有这个扩展。
- **embedding 和 rerank 仍然直连。** 打算在网关里做成"单候选、只计量、不降级"的透传：换一个模型，向量空间或打分就不可比了，所以不能降级。
- **迁移期的对账。** 直连和网关并存时，直连调用应当用单独的百炼 workspace 或 key，对账只导入网关那把 key 的账单。百炼能不能按 key 导出账单，没有核实过。
- 改写和判定的 mode 字符串仍是 `QWEN3_8_FLASH_*`。它表示 prompt 和 schema 的版本；实际由哪个模型回答，看 `modelCallDiagnostics`。
