# V0.6.1 — Knowledge Grounding Foundation

## 1. 目标

V0.5 已经证明 Agent 可以自主调用多个真实 IoT Tool，并在 V0.5.1 中约束事实、推断和 UNKNOWN 的边界。

V0.6 的下一步不是让模型“知道更多”，而是建立一个可治理的 Knowledge Grounding 链路：

```text
实时 IoT 事实
+
静态知识依据
+
来源引用
+
证据边界
=
可解释诊断建议
```

## 2. 为什么不直接上向量库

如果直接做 PDF -> Embedding -> Elasticsearch，而没有先固定：

- 文档数据模型；
- Chunk 规则；
- Retriever SPI；
- Tool Result；
- Citation；
- “知识 != 事实”的 Prompt 契约；

那么向量检索即使能返回文本，也无法判断 Agent 是否正确 Ground。

因此 V0.6.1 先使用确定性的 `LEXICAL_V1` Retriever 验证完整语义链。
V0.6.2 再替换 Retriever 实现为 Embedding + Elasticsearch / Hybrid Retrieval。

上层 `search_knowledge` Tool 不需要跟着换接口。

## 4. 数据模型

```text
af_knowledge_document
  id
  title
  source_type
  source_ref
  content
  enabled
  created_at
  updated_at
       |
       +----< af_knowledge_chunk
                id
                chunk_index
                content
                char_count
```

V0.6.1 Chunk 默认：

```text
maxChars = 800
overlapChars = 120
```

## 5. Source Type

支持：

```text
MANUAL
TROUBLESHOOTING
SOP
PLATFORM
TEST
```

`sourceRef` 只记录来源标识，例如文件名、内部文档编号或 URL。
V0.6.1 不自动抓取该 URL。

## 6. API

创建知识文档：

```http
POST /api/v1/knowledge/documents
```

示例：

```json
{
  "title": "设备离线排查 - V0.6 验收知识",
  "sourceType": "TEST",
  "sourceRef": "acceptance://v0.6/offline",
  "content": "设备长时间离线时，按顺序检查供电、SIM/流量状态、蜂窝网络覆盖和设备固件运行状态。该流程只是排查顺序，不能仅凭离线状态确认具体根因。"
}
```

搜索：

```http
POST /api/v1/knowledge/search
```

```json
{
  "query": "设备长期离线应该如何排查",
  "topK": 5
}
```

文档：

```http
GET    /api/v1/knowledge/documents
GET    /api/v1/knowledge/documents/{id}
DELETE /api/v1/knowledge/documents/{id}
```

## 7. Tool Result 语义

`search_knowledge` 返回：

```text
retrievalMode = LEXICAL_V1
groundingSemantics = STATIC_KNOWLEDGE_NOT_RUNTIME_FACT

hits[]
  rank
  citationId
  documentId
  chunkId
  chunkIndex
  title
  sourceType
  sourceRef
  content
  score
```

Citation ID：

```text
KB:{documentId}#{chunkIndex}
```

Agent 在最终回答中引用知识规则时必须原样带出，例如：

```text
根据排查手册，应先检查供电和 SIM 状态。[KB:xxx#0]
```

## 8. Grounding Agent

新增：

```text
iot-knowledge-diagnostic
```

绑定：

```text
query_device_status
query_device_properties
query_device_events
search_knowledge
```

不绑定任何 Write Tool。

证据优先级不是简单的“知识覆盖事实”，而是职责分离：

```text
设备现在是什么状态
-> IoT Tool

字段/功能是什么意思
-> Knowledge

应该按什么顺序排查
-> Knowledge

具体根因是什么
-> 只有实时/历史证据能确认；知识只能提供候选与步骤
```

## 9. V0.6.1 验收

先创建一条明确标记 `TEST` 的验收知识，避免把模型常识冒充厂商手册。

然后用新 Session 问：

```text
Device 373 is offline. Diagnose its current condition and use the knowledge base to recommend the next troubleshooting steps. Separate observed facts from knowledge-based guidance and cite the knowledge sources.
```

必须确认：

1. Agent 自主调用 IoT Tool；
2. Agent 自主调用 `search_knowledge`；
3. Knowledge Tool 为 LOW/read-only；
4. Knowledge hit 包含 citationId；
5. 最终回答把实时事实和静态知识分开；
6. 建议步骤带 Knowledge citation；
7. 不把 TEST 知识中的候选原因说成已确认根因；
8. Durable Trace 能看到 knowledge Tool Call / Result。

## 10. 当前规模边界

`LEXICAL_V1` 会从 MySQL 读取最多 5000 个已启用 Chunk 并在 JVM 内打分。

适合：

- 本地研发；
- V0.6 语义验收；
- 小规模知识集合。

不适合：

- 数十万 Chunk；
- 语义同义词检索；
- 多语言高召回；
- ANN 向量检索。

这些由 V0.6.2 的 Elasticsearch / Embedding / Hybrid Retriever 解决。
