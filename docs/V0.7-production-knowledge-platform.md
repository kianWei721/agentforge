# V0.7 — Production Knowledge Platform

## 1. 版本目标

V0.6.3 已证明 Knowledge Pipeline 能正确工作。V0.7 开始把它推进到可量化、可回归、可隔离评测、可安全重建的 Production Knowledge Platform。

## 2. Slice 1 — Multi-document Gold Dataset + Evaluation Harness

V0.6.3 的 12 Case 只有 1 篇主要 TEST 文档，只能证明没有语义回归，不能证明 Recall@K / MRR uplift。

V0.7-GOLD-1 当前包含：

```text
documents = 10
cases = 24
answerable = 20
no-answer = 4
```

所有语料都是 evaluation-only synthetic knowledge，只用于检索工程评测，不代表真实设备协议或生产业务事实。

## 3. 强隔离设计

Gold Dataset 不写入 `af_knowledge_document / af_knowledge_chunk`。

```text
Production:
MySQL -> Knowledge Source of Truth
ES -> agentforge-knowledge-v1

Evaluation:
classpath JSON -> embedding -> dedicated ES index
                     agentforge-knowledge-eval-v070
```

启动时强制校验 evaluationIndex != productionIndex，相同则拒绝启用 Evaluation Harness。

## 4. A/B 评测

一次 `POST /api/v1/knowledge/evaluation/run` 跑两套 Pipeline：

```text
HYBRID_BASELINE
Query Rewrite OFF
Rerank ON
Answerability Judge ON

HYBRID_REWRITE
Query Rewrite ON
Rerank ON
Answerability Judge ON
```

两边使用相同 Embedding、ES corpus、RRF、Reranker、Judge、TopK，唯一差异是 Query Rewrite。

## 5. 指标

Answerable Case：Recall@1、Recall@3、Recall@5、MRR。

No-answer Case：No-answer Accuracy。

整体：Overall Accuracy、Rewrite - Baseline Delta。

当前指标是完整 Pipeline 的 end-to-end 指标，即 Answerability Judge 过滤后的最终 Hit；不要和纯 Candidate Generator Recall 混用。

## 6. Safe Evaluation Rebuild

Gold Corpus 有明确上界。Harness 会先完成全部 evaluation document embedding，全部成功后才 recreate 独立 Eval Index，然后 index + refresh + run metrics。

因此凭据、Quota 或 Embedding Provider 失败不会先破坏已有 Eval Index。

## 7. 配置与运行

```text
AGENTFORGE_KNOWLEDGE_EVALUATION_ENABLED=true
AGENTFORGE_KNOWLEDGE_EVALUATION_INDEX=agentforge-knowledge-eval-v070
AGENTFORGE_KNOWLEDGE_EVALUATION_DATASET=classpath:knowledge/eval/v070-gold-dataset.json
AGENTFORGE_KNOWLEDGE_EVALUATION_TOP_K=5
```

```powershell
.\scripts\configure-knowledge-evaluation.ps1
.\scripts\evaluate-rag-v070.ps1
```

## 8. 第一轮验收原则

第一轮不预设 Recall@5 / MRR / No-answer Accuracy 阈值。正确顺序是：先建立 Gold Dataset -> 跑真实 Baseline -> 审核失败 Case -> 判断是 Dataset / Recall / Ranking / Answerability 问题 -> 再制定 Quality Gate。

## 9. 后续 V0.7 路线

Slice 1B：BM25-only vs Vector-only vs Hybrid，区分 Candidate-stage 与 end-to-end 指标。

Slice 2：Versioned physical ES indices -> build -> validate -> atomic alias swap -> rollback。

Slice 3：Evaluation history persistence、Quality Gate、CI regression summary、operational dashboards。


## 10. Evaluation Client Timeout

V0.7 Slice 1 的评测接口当前是同步 calibration endpoint。一次运行包含 10 篇文档 embedding，以及 24 Case 的 Rewrite OFF / ON 两套完整 Pipeline，因此真实运行时间可能超过 .NET `HttpClient` 默认约 100 秒超时。

PowerShell runner 默认将客户端超时设置为 900 秒：

```powershell
.\scripts\evaluate-rag-v070.ps1
```

如当前模型服务较慢，可显式提高：

```powershell
.\scripts\evaluate-rag-v070.ps1 -RequestTimeoutSeconds 1200
```

这只是评测客户端等待时间，不修改 DashScope / Elasticsearch 单次请求的 provider timeout，也不改变 Production Runtime。后续如果 Evaluation Harness 进入长期平台能力，应改造成异步 Job + progress/result 查询，而不是无限延长同步 HTTP 请求。
