# V0.7 — Production Knowledge Platform

## 1. 版本目标

V0.6.3 已证明 Knowledge Pipeline 能正确工作。V0.7 开始把它推进到可量化、可回归、可隔离评测、可安全重建的 Production Knowledge Platform。

## 2. Slice 1 — Multi-document Gold Dataset + Evaluation Harness

V0.6.3 的 12 Case 只有 1 篇主要 TEST 文档，只能证明没有语义回归，不能证明 Recall@K / MRR uplift。

V0.7-GOLD-1 当前包含：

```text
documents = 10
cases = 24
answerable = 20
no-answer = 4
```

所有语料都是 evaluation-only synthetic knowledge，只用于检索工程评测，不代表真实设备协议或生产业务事实。

## 3. 强隔离设计

Gold Dataset 不写入 `af_knowledge_document / af_knowledge_chunk`。

```text
Production:
MySQL -> Knowledge Source of Truth
ES -> agentforge-knowledge-v1

Evaluation:
classpath JSON -> embedding -> dedicated ES index
                     agentforge-knowledge-eval-v070
```

启动时强制校验 evaluationIndex != productionIndex，相同则拒绝启用 Evaluation Harness。

## 4. A/B 评测

一次 `POST /api/v1/knowledge/evaluation/run` 跑两套 Pipeline：

```text
HYBRID_BASELINE
Query Rewrite OFF
Rerank ON
Answerability Judge ON

HYBRID_REWRITE
Query Rewrite ON
Rerank ON
Answerability Judge ON
```

两边使用相同 Embedding、ES corpus、RRF、Reranker、Judge、TopK，唯一差异是 Query Rewrite。

## 5. 指标

Answerable Case：Recall@1、Recall@3、Recall@5、MRR。

No-answer Case：No-answer Accuracy。

整体：Overall Accuracy、Rewrite - Baseline Delta。

当前指标是完整 Pipeline 的 end-to-end 指标，即 Answerability Judge 过滤后的最终 Hit；不要和纯 Candidate Generator Recall 混用。

## 6. Safe Evaluation Rebuild

Gold Corpus 有明确上界。Harness 会先完成全部 evaluation document embedding，全部成功后才 recreate 独立 Eval Index，然后 index + refresh + run metrics。

因此凭据、Quota 或 Embedding Provider 失败不会先破坏已有 Eval Index。

## 7. 配置与运行

```text
AGENTFORGE_KNOWLEDGE_EVALUATION_ENABLED=true
AGENTFORGE_KNOWLEDGE_EVALUATION_INDEX=agentforge-knowledge-eval-v070
AGENTFORGE_KNOWLEDGE_EVALUATION_DATASET=classpath:knowledge/eval/v070-gold-dataset.json
AGENTFORGE_KNOWLEDGE_EVALUATION_TOP_K=5
```

```powershell
.\scripts\configure-knowledge-evaluation.ps1
.\scripts\evaluate-rag-v070.ps1
```

## 8. 第一轮验收原则

第一轮不预设 Recall@5 / MRR / No-answer Accuracy 阈值。正确顺序是：先建立 Gold Dataset -> 跑真实 Baseline -> 审核失败 Case -> 判断是 Dataset / Recall / Ranking / Answerability 问题 -> 再制定 Quality Gate。

## 9. 后续 V0.7 路线

Slice 1B：BM25-only vs Vector-only vs Hybrid，区分 Candidate-stage 与 end-to-end 指标。

Slice 2：Versioned physical ES indices -> build -> validate -> atomic alias swap -> rollback。

Slice 3：Evaluation history persistence、Quality Gate、CI regression summary、operational dashboards。


## 10. Evaluation Client Timeout

V0.7 Slice 1 的评测接口当前是同步 calibration endpoint。一次运行包含 10 篇文档 embedding，以及 24 Case 的 Rewrite OFF / ON 两套完整 Pipeline，因此真实运行时间可能超过 .NET `HttpClient` 默认约 100 秒超时。

PowerShell runner 默认将客户端超时设置为 900 秒：

```powershell
.\scripts\evaluate-rag-v070.ps1
```

如当前模型服务较慢，可显式提高：

```powershell
.\scripts\evaluate-rag-v070.ps1 -RequestTimeoutSeconds 1200
```

这只是评测客户端等待时间，不修改 DashScope / Elasticsearch 单次请求的 provider timeout，也不改变 Production Runtime。后续如果 Evaluation Harness 进入长期平台能力，应改造成异步 Job + progress/result 查询，而不是无限延长同步 HTTP 请求。

## 11. Slice 1A 真实结论

V0.7-GOLD-1（10 documents / 24 cases）真实运行时，Baseline 与 Rewrite 的 Recall@1/3/5、MRR、No-answer Accuracy、Overall Accuracy 全部为 1.0。

该结果首先证明 Evaluation Harness 与隔离索引正确工作，但也说明 GOLD-1 主题区分过强，产生 Ceiling Effect。它不能用于证明 Query Rewrite uplift、RRF k=60 最优或 Hybrid 一定优于单路检索。

## 12. Slice 1B — Candidate-stage Benchmark

Slice 1B 把指标拆成两层：

```text
Candidate stage (pre-reranker / pre-judge)
BM25 | Vector | Hybrid RRF
-> Recall@1/3/5 + MRR

End-to-end
Hybrid -> Reranker -> Answerability Judge
-> final Recall@K + No-answer Accuracy + Overall Accuracy
```

这样可以区分“Candidate 本身召回正确”与“Candidate 排序较差但被 Reranker 救回”。

## 13. RRF k Sweep 设计

当前 production candidate window 在 topK=5、candidateMultiplier=4 下为 20。默认 sweep 选用 5 / 20 / 60 / 120，不是预设 60 应该赢，而是覆盖不同 rank-decay 形态：

```text
k=5   : rank 头部权重明显
k=20  : k 与 candidate window 同量级
k=60  : RRF 经典 / Elasticsearch baseline
k=120 : 相对 candidate window 已非常平滑
```

参数可通过 `AGENTFORGE_KNOWLEDGE_EVALUATION_RRF_K_VALUES` 修改。评测同时对 Original Query 与 Query Rewrite 后的 Query 运行同一组 variant。

## 14. V0.7-GOLD-2 Hard Negatives

GOLD-2 扩展到 20 documents / 34 cases。不同文档不再按完全独立主题组织，而是在 offline、shadow、signal、peripheral、event 等主题簇内加入语义相近文档，例如 Offline Procedure / Threshold Policy / Alarm Policy / Historical Statistics。

这些文档会共享 offline、SignalStrength、PeripheralStatus、shadow 等词，从而让 BM25、Vector、RRF 和 Rewrite 真正产生可比较的排名差异。

所有 GOLD-2 文档依旧是 evaluation-only synthetic knowledge，不得当作生产协议事实。


## 15. Slice 1B-2 — Channel Disagreement Corpus

GOLD-2 的真实结果已经产生 BM25 / Vector 差异，但 corpus=20 与 candidateWindow=20 仍使 Vector/RRF 接近全量排序，因此 RRF k sweep 无法形成可解释差异。

GOLD-3 扩展为：

```text
documents = 80
cases = 34
candidateWindow = 20
corpus / window = 4x
```

新增 60 个 lexical hard negatives，围绕 offline / shadow / signal / peripheral / event / network 六个主题簇重复 exact tokens、错误码和诊断词，但明确不提供目标答案。目的是制造 BM25 与 Vector 的 Channel Disagreement，而不是制造更多无意义随机文档。

## 16. Retrieval Stage Diagnostics

只对下列 Case 做额外 Stage Replay：

```text
1. Baseline 或 Rewrite end-to-end failed
2. BM25 与 Vector 的 relevant rank 不一致
3. production RRF k 的 relevant rank != 1
```

每个选中 Case 分 ORIGINAL / REWRITE 两路记录：

```text
BM25 rank + top3
Vector rank + top3
RRF rank + top5
Rerank rank + top5
Judge decision
Judge reasonCode for expected document
Final rank / final no-answer
```

Stage Replay 使用 production RRF k，只用于定位最终失败在哪一层；完整 k sweep 仍由 Candidate Benchmark 承担。这样避免把所有 34 Case 再执行一次昂贵 Rerank/Judge。


## 17. Slice 1B-3 — Channel-specific Query Strategy

GOLD-3 真实结果显示 Query Rewrite 对 BM25 Recall 有明显增益，但 Vector Original 的指标高于 Vector Rewrite。因此不能继续假设一个 rewrittenQuery 应同时服务 lexical 与 semantic 两路，也不能直接因为观察到这一点就只测试一个偏好的方案。

Slice 1B-3 使用完整 2×2 Query Strategy Matrix：

```text
Strategy A ORIGINAL
BM25=original, Vector=original

Strategy B REWRITE
BM25=rewrite, Vector=rewrite
(current production query behavior when rewrite is enabled)

Strategy C BM25_REWRITE_VECTOR_ORIGINAL
BM25=rewrite, Vector=original

Strategy D BM25_ORIGINAL_VECTOR_REWRITE
BM25=original, Vector=rewrite
(control for the opposite asymmetric hypothesis)
```

四种 Strategy 分别与全部 RRF k sweep 组合。这样避免只验证“Rewrite 给 BM25、Original 给 Vector”这一条事后看起来合理的假设。

## 18. RRF Parameter Confirmation Policy

候选阶段排序采用固定 lexicographic policy：

```text
1. Recall@5
2. Recall@3
3. MRR
4. Recall@1
```

原因是 RRF 下游仍有 qwen3-rerank，Candidate Generator 的第一职责是让正确知识进入有限候选池，其次才是候选内部次序。

如果多个 Variant 在四个指标上完全相同，报告保留所有 Leading Variants，不使用更小 k、更接近默认值、或更好看的单项指标做任意 tie-break。

报告会同时给出：

```text
productionVariant
productionRrfK
productionOnLeadingFrontier
leadingVariants
leadingQueryModes
leadingRrfKValues
leader - production deltas
```

Decision Boundary 固定为：

```text
CALIBRATION_ONLY_NO_AUTO_PRODUCTION_CHANGE
```

因此 Slice 1B-3 的 Candidate 结果只能确定 leading configuration。真正修改 Production Query Routing / RRF k 之前，还需要对 leading configuration 做一次 end-to-end confirmation，验证 Reranker、Answerability、No-answer 与真实 Runtime 不发生回归。


## 19. Controlled Rewrite Plan

Slice 1B-3 的 Query Strategy Matrix 依赖同一 rewrittenQuery 被多个 Variant 重放。评测不再在 Candidate、End-to-End、Stage Diagnostics 三个阶段重复调用 Query Rewrite Provider。

新的 Evaluation Rewrite Plan：

```text
dataset cases
-> unique original queries
-> Query Rewrite provider once per unique query
-> validation
-> immutable rewrite plan
-> Candidate Matrix replay
-> End-to-End replay
-> Stage Diagnostics replay
```

Evaluation-only rewrite 最多允许 2 次尝试，第二次仅用于吸收瞬时 provider/timeout 故障；参数校准仍要求最终 rewrite 成功，不允许静默 fallback 到 original query。

如果两次都失败，409 错误会包含：

```text
case name
attempt count
sanitized provider failure
```

而不是原来的泛化消息。

Rewrite Plan 在 isolated evaluation index recreate 之前构建，因此 Query Rewrite Provider 故障不会先销毁已有 Eval Index。

Production Runtime 的 Query Rewrite fail-open、15s provider request timeout 与现有行为不变；本改动只作用于 Evaluation Harness。


## 20. Evaluation Elasticsearch Resilience

Slice 1B-3 的 Candidate Matrix 会执行大量 Elasticsearch read queries。Production ES 默认 timeout 仍保持：

```text
connectTimeout = 2s
requestTimeout = 5s
```

Evaluation Harness 不再原样继承这个较紧的运行时 timeout，而是只对 isolated evaluation backend 使用下限：

```text
connectTimeout >= 5s
requestTimeout >= 15s
```

并且仅对幂等的 lexical / vector search 允许最多 2 次尝试，间隔 200ms。Index recreate / bulk / refresh 不做自动 retry。

这样可以吸收 calibration batch 中的瞬时网络抖动，同时不改变 Production Runtime 的 Elasticsearch timeout/retry 语义。

Elasticsearch transport error 也改为保留安全诊断信息：

```text
method
path
timeout
exception type
```

不输出 Base URL、认证头或请求正文。


## 21. Slice 1B-3 End-to-End Confirmation

Candidate-stage Matrix 的唯一 Leader 不能直接等价为 Production 最优，因为下游还有 qwen3-rerank 与 Answerability Judge。因此增加第二道 promotion gate。

Control 固定为当前 Production 查询行为：

```text
REWRITE
+
production rrfK
+
Reranker
+
Answerability
```

Challenger 来自本轮 Candidate Benchmark 的 unique leader。当前已知 leader 为 `ORIGINAL + k=5`，但每轮运行仍重新计算，不把该结果硬编码成评测结论。

End-to-End promotion 条件：

```text
candidate leader remains unique
AND no new failed case
AND Recall@1 challenger >= control
AND Recall@3 challenger >= control
AND Recall@5 challenger >= control
AND MRR challenger >= control
AND NoAnswerAccuracy challenger >= control
AND OverallAccuracy challenger >= control
```

满足时只输出：

```text
PROMOTION_ELIGIBLE
```

否则：

```text
HOLD_PRODUCTION
```

该状态仍是 Evaluation Gate，不自动修改 Production Query Rewrite 或 RRF k。Production 变更必须人工提交，并做 Runtime smoke/regression 验证。

## 22. GOLD-3.1 Answerability Correction

此前 `offline-alarm-debounce` Query 问“为什么做 debounce 和重复观察窗口”，但 Gold 文档只说“可能使用”，没有提供原因。Judge 因此以 `INSUFFICIENT_EVIDENCE / TOPIC_ONLY` 拒绝是合理行为。

GOLD-3.1 不放宽 Judge，而是补齐该 synthetic policy document 的直接语义：

```text
debounce / repeated observation
-> reduce false positives from transient connectivity loss or brief telemetry gaps
-> require the condition to persist before notification
```

这属于 Gold Label / Gold Evidence 对齐修复，不代表真实设备协议事实。


## 23. E2E Confirmation v2 — Targeted Regression Recheck

第一次 E2E Promotion Gate 的 Challenger-only failure 是 `reconnect-backoff-purpose`。该 Case 的 Candidate 已进入 Top5，但 Answerability 结果与同轮 Stage Replay 出现不一致，因此需要把 Gold Evidence mismatch 与 Judge variance 分开处理。

### GOLD-3.2

`eval-reconnect-backoff` 增加直接 rationale：

```text
tight reconnect loop
-> repeated retries while network/dependency may still be unavailable
-> retry storm
-> unnecessary network/radio/CPU/runtime load

bounded backoff
-> reduce repeated load during sustained failure
```

仍保留 “exact backoff ceiling 未提供” 的 No-answer 边界。该文本只属于 synthetic evaluation knowledge。

### Targeted Recheck

只对第一次完整 Control vs Challenger 中的 `initialNewFailureCases` 做额外重放，不对全部 34 Case 连跑多轮。

每个 Case：

```text
3 Control trials
3 Challenger trials
```

调用顺序按 trial 交替 Control-first / Challenger-first，降低长批次中固定执行顺序造成的时间偏差。

判定规则：

```text
3/3 Control PASS + 3/3 Challenger PASS
= CLEARED_TRANSIENT

3/3 Control PASS + 0/3 Challenger PASS
= CONFIRMED_REGRESSION

any mixed outcome
= UNSTABLE
= HOLD_FOR_STABILITY
```

只有 `CLEARED_TRANSIENT` 会进入 metrics stabilization：从 3 次 passing trial 中选对 Challenger 最保守的 passing result（answerable Case 取最差 relevant rank）替换首次偶发失败，然后重新计算 Recall/MRR/Accuracy。

这避免用一次 Judge 波动直接淘汰 Challenger，也避免用 2/3 多数票轻易放行 Production Promotion。

没有 initial challenger-only failure 时，不发生额外 recheck 调用。

## 24. Promotion Decision v2

最终决策仍要求：

```text
unique Candidate Leader
AND no confirmed regression
AND no unstable recheck
AND stabilized challenger has no new failure
AND Recall@1/3/5 non-regressing
AND MRR non-regressing
AND NoAnswerAccuracy non-regressing
AND OverallAccuracy non-regressing
```

输出：

```text
PROMOTION_ELIGIBLE
HOLD_PRODUCTION
HOLD_FOR_STABILITY
```

任何状态都不会自动写入 Production Query Rewrite / RRF 配置。
