# V0.3 — Real IoT HTTP Tool Adapter

## 1. 目标

此前 `query_device_status` 的调用链已经具备：

```text
LLM
  -> Tool Selection
  -> Tool Arguments
  -> AgentForge Tool
  -> DeviceStatusQueryPort
  -> DemoDeviceStatusQueryAdapter
```

但最后一步仍返回确定性演示数据。

本阶段把 Port 保留不动，只增加真实 Adapter：

```text
DeviceStatusQueryPort
  ├─ DemoDeviceStatusQueryAdapter
  └─ HttpDeviceStatusQueryAdapter
```

这样 Agent / Tool Domain 不依赖具体 IoT 平台、HTTP Client 或认证方式。

## 2. 真实后端契约

本阶段依据真实 yudao-cloud-mini-master 的 Device Web Controller 接入：

```http
GET /admin-api/device/web/devices/{deviceId}
Authorization: Bearer <access-token>
tenant-id: <tenant-id>
Accept: application/json
```

Controller 源码路径：

```text
yudao-module-device/
  yudao-module-device-biz/
    src/main/java/cn/iocoder/yudao/module/device/controller/admin/mini/
      DeviceWebController.java
```

基础信息 Response DTO：

```text
DeviceInfoDTO
```

包含：

```text
deviceId
deviceName
deviceNickname
productId
state
location
province/city/county
longitude/latitude
autoLocationEnabled
locationSource
lastReceiveTime
registerTime
```

服务端 `CommonResult` 成功码为 `200`。

## 3. Port / Adapter 为什么保持分离

Tool 只认识：

```java
DeviceStatusQueryPort
```

不认识：

```text
HttpClient
Authorization
tenant-id
/admin-api/...
Yudao CommonResult
```

因此未来切换：

```text
REST
gRPC
内部 RPC
MQTT Shadow
另一家 IoT 平台
```

不需要修改 `DeviceStatusTool`。

这属于 Hexagonal Architecture（六边形架构）中的 Port / Adapter 边界。

## 4. Tool Security Boundary

LLM 只能生成：

```json
{"deviceId":"367"}
```

它不能生成或修改：

```text
base URL
path template
Authorization
tenant-id
timeout
retry
```

并且 deviceId 必须匹配：

```text
^[0-9]{1,19}$
```

所以类似：

```text
../admin
https://other-host/
367?tenant-id=...
```

会在进入 HTTP Adapter 前被拒绝。

这是 Agent Tool 与普通“模型帮我拼 URL”之间的重要安全边界。

## 5. Authentication

真实后端使用：

```text
Authorization: Bearer <token>
tenant-id: <tenant>
```

AgentForge 的 Token 只从本地/部署环境配置读取。

环境变量：

```text
AGENTFORGE_IOT_DEVICE_STATUS_MODE=http
AGENTFORGE_IOT_BASE_URL=...
AGENTFORGE_IOT_ACCESS_TOKEN=...
AGENTFORGE_IOT_TENANT_ID=...
```

仓库不会保存真实 Token。

HTTP Adapter 不会把 Token、内部 Base URL 或后端原始错误正文放进 ToolResult，因此这些信息也不会进入 LLM Context / Tool Trace。

## 6. 当前身份模型

V0.3 使用的是：

```text
AgentForge Service Credential
固定后端身份
+
固定 tenant-id
```

而不是：

```text
Agent user token
  -> 透传
  -> IoT backend
```

所以当前权限边界是：

```text
IoT service credential
+ tenant/device permission
```

不是 AgentForge userId 级别的终端用户授权。

后续如果 AgentForge 自身进入多租户生产模式，需要引入 Credential Delegation / Token Exchange，而不是让 LLM 接触用户 Token。

## 7. Response Normalization

真实后端设备基础信息接口返回的状态是中文：

```text
在线
离线
休眠
未激活
```

Tool Domain 归一化为：

```text
ONLINE
OFFLINE
SLEEP
INACTIVE
```

同时保留：

```text
attributes.stateRaw
```

所以 Agent 面向统一状态语义，但诊断时仍能看到原始业务值。

`lastReceiveTime` 当前保持后端原始字符串，不伪造不存在的时区信息。

## 8. Timeout

HTTP Client 分两个超时：

```text
connect-timeout = 2s
request-timeout = 3s
```

连接超时解决“根本连不上”。

Request Timeout 约束整个设备详情查询。

Agent Tool 不应该因为一个慢下游无限占用执行线程。

## 9. Reactive / Blocking Boundary

JDK `HttpClient.send` 是阻塞调用。

因此 `AgentScopeToolAdapter.callAsync` 现在显式：

```text
Mono.fromCallable(...)
  .subscribeOn(Schedulers.boundedElastic())
```

避免阻塞 Reactor / AgentScope 的响应式执行线程。

## 10. Retry

设备状态查询是：

```http
GET
```

属于 read-only + idempotent（只读且幂等）。

所以允许有限重试：

```text
max-attempts = 2
retry-backoff = 150ms
```

只对：

```text
timeout
transport failure
HTTP 5xx
business 500 / 503
```

这类瞬时故障重试。

不会对：

```text
401
403
bad request
invalid response
```

重试。

因此这里的 Retry 是有语义条件的，不是“失败就无脑再试”。

## 11. Circuit Breaker

当前实现轻量级 Circuit Breaker：

```text
连续 3 个最终瞬时失败
  -> OPEN 30s
```

OPEN 时新的 Tool 请求直接返回：

```text
CIRCUIT_OPEN
```

避免下游已经明显故障时，每一次 LLM Tool Call 都继续等待网络 Timeout。

当前是进程内熔断状态，不做 Redis 分布式共享。

## 12. Error Mapping

HTTP / Backend 错误被归一化为：

```text
AUTHENTICATION_FAILED
FORBIDDEN
BAD_REQUEST
BACKEND_UNAVAILABLE
TIMEOUT
CIRCUIT_OPEN
INVALID_RESPONSE
INTERRUPTED
```

ToolResult 只返回：

```text
device status query unavailable: <REASON>
```

不会把：

```text
Access Token
内部地址
后端堆栈
后端敏感错误正文
```

直接交给模型。

注意：Tool Error 不一定代表整个 Agent Execution FAILED。

AgentScope 可以拿到 ToolResultState.ERROR，再由模型生成“当前无法查询设备”的最终回答；这种情况下 Execution 仍可能成功结束。

## 13. 配置

默认仍为：

```text
mode=demo
```

所以升级代码不会因为缺少真实 IoT Token 直接导致本地启动失败。

切换真实 HTTP：

```powershell
.\scripts\configure-iot.ps1
```

脚本安全写入忽略的 `.env.local`。

配置：

```yaml
agentforge:
  iot:
    device-status:
      mode: http
      base-url: ...
      detail-path: /admin-api/device/web/devices/{deviceId}
      access-token: ...
      tenant-id: ...
      connect-timeout: 2s
      request-timeout: 3s
      max-attempts: 2
      retry-backoff: 150ms
      circuit-breaker-failure-threshold: 3
      circuit-breaker-open-duration: 30s
```

生产环境建议 Base URL 使用 HTTPS；V0.3 为兼容内网测试环境仍允许 HTTP。

## 14. Health

```http
GET /api/v1/system/health
```

新增：

```text
milestone = V0.3-real-iot-http-tool-adapter
iotDeviceStatusAdapter = demo | http
iotDeviceStatusConfigured = true | false

```

Health 不返回 Base URL、tenant-id 或 Token。

### 15.4 Agent Tool Calling

使用一个当前后端账号/租户确实可见的 deviceId。

```powershell
$payload = @{
    userId = "iot-http-user"
    sessionId = "iot-http-verify-001"
    message = "Check device 367 with query_device_status. You must use the tool and tell me its current status and last report time."
} | ConvertTo-Json

$response = Invoke-WebRequest `
    -Method Post `
    -Uri "http://localhost:8080/api/v1/agents/default/stream" `
    -ContentType "application/json; charset=utf-8" `
    -Body $payload `
    -UseBasicParsing

$response.Content
```

验收重点：

```text
toolName = query_device_status
tool_result_end.state = success
Tool Result source = yudao-device-web-http
status 不再来自 demo-adapter
lastSeenAt 对应真实后端 lastReceiveTime
```

### 15.5 Trace

```powershell
Invoke-RestMethod "http://localhost:8080/api/v1/executions/$executionId/traces" |
  ConvertTo-Json -Depth 10
```

确认 Trace 里 Tool Result 已是 `yudao-device-web-http`。

## 16. 当前边界

1. 当前只接入 Device Detail GET，只读。
2. 当前 Service Credential 是静态配置，不做自动刷新。
3. Token 过期会返回 AUTHENTICATION_FAILED，需要人工更新配置。
4. 当前熔断器为单 JVM 状态。
5. 还没有把真实 IoT HTTP latency / status code 单独结构化成 Trace 字段。
6. 写操作 Tool 尚未开放；未来控制设备必须重新设计 Permission、Confirmation、Idempotency 与 Audit 边界。
7. 真实 Device Web Endpoint 自身会执行菜单权限与租户/设备归属检查；AgentForge 不绕过该检查。
8. 小程序 `/device/mini/devices/{deviceId}` 对产品 25/26/27/28/29/31 还要求 `baseId` 基地范围；本阶段因此改用 Web 基础信息接口，避免把基地 ID 暴露为 LLM Tool 参数。

完成真实后端成功查询、Trace 验证和至少一次错误路径验证后，本阶段才正式关闭。
