# V0.4 — Tool Governance & Resilience

## 1. 阶段目标

V0.3 已经证明 AgentForge 能安全调用真实 IoT HTTP 后端。真实联调同时暴露了新的运行时问题：

```text
Tool Call
  -> AUTHENTICATION_FAILED / FORBIDDEN / BAD_REQUEST
  -> 模型再次用完全相同参数调用同一 Tool
  -> 下游请求没有任何新信息，却重复消耗延迟、Token 与后端配额
```

V0.4 开始解决“Tool 已经能调用以后，Runtime 如何治理 Tool”。

## 2. 第一切片：Repeated Non-retryable Call Guard

规则：

```text
same Agent call
+ same tool name
+ canonical equivalent arguments
+ previous result = non-retryable failure
------------------------------------------------
block repeated invocation before business Tool executes
```

典型不可重试失败包括：

```text
AUTHENTICATION_FAILED
FORBIDDEN
BAD_REQUEST
INVALID_ARGUMENT
NOT_FOUND
```

TIMEOUT / BACKEND_UNAVAILABLE 等 retryable failure 不会被这一规则直接阻断。

## 3. 为什么必须是 call-scoped

不能把失败永久缓存到 Session。

下一轮请求时可能已经发生：

```text
Token 刷新
权限调整
设备重新绑定
下游恢复
```

AgentScope v2 RuntimeContext 是单次 call 的上下文，因此当前实现：

```text
one Agent call
  -> one RuntimeContext
  -> one ToolGovernanceState
```

调用结束后 Ledger 自然释放，不污染下一轮对话。

## 4. 参数指纹

参数递归规范化，Map key 排序，再计算 SHA-256：

```text
toolName + canonical arguments
  -> SHA-256
  -> argumentFingerprint
```

因此 Map 的字段顺序不同不会绕过 Guard。

Trace 记录 fingerprint，不为了治理额外复制完整 Tool 参数。

## 5. ToolResult Failure Semantics

原 ToolResult 只有：

```text
success
message
data
```

V0.4 增加 Runtime 内部机器语义：

```text
failureCode
retryable
```

例如：

```text
success=false
failureCode=FORBIDDEN
retryable=false
```

治理代码不再解析自然语言 message。

`toModelText()` 仍保持 `success/message/data`，不会额外把内部治理字段暴露给模型。

## 6. Guard 行为

第一次：

```text
query_device_status(999999999)
  -> real backend
  -> FORBIDDEN
  -> record fingerprint
```

同一 Agent call 的第二次相同调用：

```text
query_device_status(999999999)
  -> ToolGovernanceState
  -> BLOCK
  -> DeviceStatusTool / HTTP Adapter 不执行
  -> ToolResult ERROR: REPEATED_NON_RETRYABLE_CALL
```

Guard 返回 ToolResult，而不是抛出 Runtime 异常，因此 Agent 仍可以继续推理并正常结束。

## 7. Structured Governance Trace

Flyway V4 为 `af_trace_event` 增加：

```text
tool_duration_ms
failure_code
retryable
governance_decision
governance_reason
argument_fingerprint
blocked_by_tool_call_id
blocked_by_failure_code
```

正常失败：

```text
failureCode=FORBIDDEN
retryable=false
governanceDecision=ALLOW
```

被阻断的重复调用：

```text
failureCode=REPEATED_NON_RETRYABLE_CALL
retryable=false
governanceDecision=BLOCK
governanceReason=repeated_non_retryable_failure
blockedByToolCallId=<first call>
blockedByFailureCode=FORBIDDEN
```

这样 Trace 能区分“真实下游执行失败”和“被 AgentForge Policy 阻断”。

## 8. 有界状态

单次 call 的治理 Ledger 默认最多记录：

```text
256
```

允许配置 1..4096，避免异常模型循环造成无界内存增长。

这不是业务级调用配额；达到上限后只是停止扩大 Ledger。

## 9. 配置

```yaml
agentforge:
  tool-governance:
    enabled: true
    block-repeated-non-retryable-calls: true
    max-recorded-invocations: 256
```

Health 暴露治理开关和容量，不暴露 Tool 参数或凭据。

## 10. 后续切片


### 并发边界

AgentScope Java 2.0.0 的默认 `ToolkitConfig` 为：

```text
parallel=false
```

所以即使模型在一次 Model Call 中同时生成两个 Tool Call，默认仍按声明顺序执行。第一次失败会先写入 `ToolGovernanceState`，第二次才进入 Guard，因此本 Slice 行为稳定。

如果未来显式开启 `parallel=true`，当前“check then record”模型需要升级为 atomic claim / in-flight deduplication（原子占位 / 执行中去重），否则两个相同调用可能并发通过前置检查。当前默认顺序执行下不构成阻塞。

**Slice 1 — Repeated Non-retryable Call Guard：CLOSED / ACCEPTED。**

## 13. Slice 2 — Structured Outbound HTTP Telemetry

下一切片开始补齐真实 HTTP 下游调用的结构化遥测：

```text
HTTP status
business code
attempt count
downstream duration
outbound outcome
```

目标是让 Trace 能直接回答：

```text
Tool 为什么失败？
是否真正访问了下游？
HTTP 层还是业务码失败？
发生了几次尝试？
下游耗时多少？
```

而不是只能从 Tool Result 文本反推。

Slice 2 已进入代码实现：真实 HTTP Adapter 现在通过 call-scoped `ToolTelemetrySink` 上报结构化遥测，Runtime 在 `tool_result_end` 汇总并持久化。

新增字段：

```text
outboundProtocol
downstreamSystem
outboundAttempts
httpStatus
businessCode
downstreamDurationMs
outboundOutcome
```

其中 `downstreamDurationMs` 表示本次 Adapter 调用的总 wall-clock 时间，包含有界 Retry 与 Retry Backoff；它不同于 `toolDurationMs`，后者覆盖整个 Tool Runtime 执行。

不会记录：

```text
Base URL
完整 path
Authorization
tenant-id
response body
```

因此结构化遥测继续遵循最小披露原则。

Flyway V5 将这些字段持久化到 `af_trace_event`。

## 15. Slice 3 — Tool Policy Layer

下一切片进入 Tool Policy Layer（工具策略层）。

需要先区分两个概念：

```text
AgentDefinition.toolNames
= Capability Exposure
= 这个 Agent 能看到哪些 Tool

Tool Policy
= Execution Authorization
= 即使 Tool 被暴露，本次调用是否允许执行
```

AgentForge 当前已经通过 `toolNames` 实现了 per-agent Tool capability allowlist，因此 Slice 3 不会再造一套重复的“Agent -> Tool allowlist”。

Slice 3 将把重点放在：

```text
risk classification
read/write semantics
policy decision
confirmation boundary
policy trace
```

目标是为未来设备控制等 Write Tool 建立：

```text
LLM proposes action
  -> Tool Policy evaluates
  -> ALLOW / DENY / REQUIRE_CONFIRMATION
  -> only then execute business Tool
```

而不是让“Tool 已经注册”自动等于“任何时候都可以执行”。

## 16. Slice 3A — Tool Risk & Execution Policy

Slice 3A 已进入代码实现，当前保持 OPEN，等待本地 Maven 与 Runtime Trace 验证。

### 16.1 Capability Exposure 与 Execution Authorization 分离

已有：

```text
AgentDefinition.toolNames
  -> 决定 Agent 能看到哪些 Tool
```

本 Slice 新增：

```text
ToolExecutionPolicy
  -> 决定一次具体 Tool Call 是否允许执行
```

因此不新增第二套 Agent -> Tool allowlist，避免两个 Source of Truth。

### 16.2 Tool Risk Metadata

`AgentTool` 新增：

```text
riskLevel = LOW / MEDIUM / HIGH
```

默认规则是 fail-safe：

```text
readOnly=true  -> LOW
readOnly=false -> HIGH
```

所以未来开发者如果只声明一个 Write Tool 而忘记显式标风险，它不会被默认为低风险。

`query_device_status` 当前显式声明：

```text
readOnly=true
riskLevel=LOW
```

`ToolDescriptor` 同时暴露 risk level，供管理面/API 观察 Tool 元数据。

### 16.3 Policy Decision Model

新增：

```text
ALLOW
DENY
REQUIRE_CONFIRMATION
```

Baseline Policy：

```text
LOW/MEDIUM read-only -> ALLOW
HIGH read-only       -> REQUIRE_CONFIRMATION
Write Tool           -> REQUIRE_CONFIRMATION
```

`DENY` 已作为一等决策进入 Runtime Contract，但 Baseline Policy 默认不任意硬编码业务 Tool 黑名单。后续可由更高层 Policy Provider、租户策略或应急 Kill Switch 返回 DENY。

### 16.4 当前 Confirmation Boundary

Slice 3A 只建立 Policy 决策，不实现确认生命周期。

因此：

```text
REQUIRE_CONFIRMATION
  -> Tool 不执行
  -> CONFIRMATION_REQUIRED
  -> outboundAttempts = 0
```

真正的：

```text
confirmationId
expiry
user binding
approve/reject
single-use consumption
audit
```

属于 Slice 3B。

这保证在确认系统未完成前，Write Tool 默认 fail closed（失败关闭），而不是先执行再补确认。

### 16.5 Policy 与 Repeated-call Governance 的顺序

执行顺序：

```text
LLM Tool Call
  -> ToolExecutionPolicy
  -> if ALLOW:
       Repeated-call Governance
       -> Business Tool
     if DENY / REQUIRE_CONFIRMATION:
       Business Tool 不执行
```

Policy 预先阻断时，Repeated-call Governance 记录：

```text
governanceDecision = SKIP
governanceReason   = policy_preempted
```

避免把“政策不允许执行”误记成“重复调用治理允许/阻断”。

同时，`POLICY_DENIED` / `CONFIRMATION_REQUIRED` 不会写入 non-retryable failure fingerprint ledger，因此不会污染后续真正的重复失败治理。

### 16.6 Policy Trace

Flyway V6 为 `af_trace_event` 增加：

```text
tool_risk_level
tool_read_only
policy_decision
policy_reason
```

在 `tool_result_end` 中可以观察：

```text
toolRiskLevel
toolReadOnly
policyDecision
policyReason
```

对于 Policy 阻断：

```text
outboundAttempts = 0
outboundOutcome  = POLICY_DENIED
```

或：

```text
outboundAttempts = 0
outboundOutcome  = CONFIRMATION_REQUIRED
```

因此 Trace 可以证明业务 Tool / HTTP 下游没有被执行。

### 16.7 配置

```yaml
agentforge:
  tool-policy:
    enabled: true
    require-confirmation-for-write-tools: true
    require-confirmation-for-high-risk-read-only: true
```

环境变量：

```text

AGENTFORGE_TOOL_POLICY_CONFIRM_WRITE
AGENTFORGE_TOOL_POLICY_CONFIRM_HIGH_RISK_READ
```

Health 暴露策略开关，不暴露 Tool 参数。

### 16.8 与 AgentScope Permission 的关系

AgentForge Policy 位于业务 Tool Adapter 内，是 AgentForge 自己的执行安全边界。

AgentScope 自身仍有 Permission Engine。当前：

```text
read-only Tool -> AgentScope Permission ALLOW
write Tool     -> AgentScope Permission PASSTHROUGH
```

因此未来 Slice 3B 做 Human-in-the-loop 时，需要明确 AgentForge Confirmation 与 AgentScope Permission/Confirmation 的集成关系，避免形成两个互相独立的确认状态机。

当前 Slice 3A 不尝试伪造一个尚不存在的确认流程。

## 18. Slice 3B — Human-in-the-loop Confirmation

下一切片进入 Human-in-the-loop Confirmation（人在回路确认）。

目标不是简单加一个“确认”布尔值，而是建立可验证、可过期、不可重放的确认事实：

```text
LLM proposes high-risk/write Tool
  -> Policy = REQUIRE_CONFIRMATION
  -> create confirmation request
  -> bind user / agent / session / tool / argument fingerprint
  -> user APPROVE or REJECT
  -> verify expiry and single-use state
  -> only approved matching invocation can execute
  -> persist confirmation + execution audit
```

Slice 3B 在设计和实现完成前保持 OPEN。


## 19. Slice 3B-1 — Durable Human-in-the-loop Confirmation

Slice 3B 先实现通用确认生命周期，不直接下发真实设备控制命令。

当前真实设备控制边界保持不变：设备控制将在 3B-2 单独接入；3B-1 不改变任何 IoT 设备状态。

### 19.1 状态机

```text
PENDING
  -> APPROVED
  -> REJECTED
  -> EXPIRED

APPROVED
  -> CONSUMED
  -> REJECTED
  -> EXPIRED
```

`CONSUMED` 是终态，并且一次确认只能消费一次。

### 19.2 绑定维度

确认不是一个独立的布尔值，而是绑定：

```text
agentId
userId
durable sessionId
toolName
argumentFingerprint
```

因此：

```text
同一个用户 + 同一个 Tool + 不同参数
!= 同一个确认
```

参数发生变化后，旧批准不能授权新操作。

### 19.3 Active Key

上述绑定计算 SHA-256 active key。

数据库只允许一个相同 binding 的活跃确认：

```text
PENDING / APPROVED -> active_key 非空且唯一
REJECTED / EXPIRED / CONSUMED -> active_key = NULL
```

MySQL UNIQUE 对多个 NULL 允许共存，因此历史终态记录不会阻止未来重新发起同一操作。

这样同时解决：

- 模型重复提出同一个待确认 Tool Call 时不会无限创建确认记录；
- APPROVED 被消费后可以重新发起新的确认；
- 并发请求通过数据库唯一约束和行锁收敛。

### 19.4 确认记录

Flyway V7 新增：

```text
af_tool_confirmation
```

核心字段：

```text
id
active_key
requested_execution_id
requested_tool_call_id
consumed_execution_id
consumed_tool_call_id
agent_id
user_id
session_id
tool_name
argument_fingerprint
summary
status
expires_at
approved_at
rejected_at
consumed_at
created_at
updated_at
```

不持久化完整 Tool Arguments。机器绑定使用 fingerprint；面向人的内容使用 Tool 自己提供的安全 `confirmationSummary`。

### 19.5 Runtime 行为

当 Policy 返回：

```text
REQUIRE_CONFIRMATION
```

Runtime：

```text
查找 matching APPROVED confirmation
  -> 有：原子 CONSUME -> effective policy ALLOW -> Tool 执行
  -> 无：创建/复用 PENDING -> Tool 不执行
```

PENDING 返回给模型的安全数据：

```text
confirmationId
status
expiresAt
toolName
summary
```

不回显原始 Tool Arguments 或凭据。

批准本身不直接执行 Tool。它只创建一张可消费的 authorization permit（授权凭证）；下一次完全匹配的 Tool invocation 才能原子消费并执行。

### 19.6 API

```http
GET  /api/v1/tool-confirmations/{confirmationId}?userId={userId}
POST /api/v1/tool-confirmations/{confirmationId}/approve
POST /api/v1/tool-confirmations/{confirmationId}/reject
```

approve/reject body：

```json
{
  "userId": "..."
}
```

当前 `userId` 是 AgentForge 应用层逻辑身份，还不是经过外部 IAM / OAuth 验证的安全主体。真正用户身份委托属于后续 Credential Boundary，不应把当前接口误认为已经完成互联网级认证授权。

### 19.7 TTL 与过期

默认：

```text
5 minutes
```

配置：

```yaml
agentforge:
  tool-confirmation:
    ttl: 5m
```

超过 TTL 的 PENDING / APPROVED 会在后续访问或消费时惰性转为 EXPIRED，并释放 active key。

### 19.8 Trace

V7 同时给 `af_trace_event` 增加：

```text
confirmation_id
confirmation_status
```

第一次被确认边界阻断：

```text
policyDecision     = REQUIRE_CONFIRMATION
confirmationStatus = PENDING
outboundAttempts   = 0
```

批准后完全匹配的下一次调用：

```text
policyDecision     = ALLOW
policyReason       = approved_confirmation
confirmationStatus = CONSUMED
```

### 19.9 单元/持久化验收覆盖

当前测试覆盖：

```text
重复相同 binding 复用同一 active confirmation
错误 userId 不可 approve
PENDING -> APPROVED
APPROVED -> CONSUMED
第二次 consume 失败
CONSUMED 后可重新创建新 confirmation
过期后不能 late approve / consume
Write Tool 在 PENDING 时 delegate executions = 0
APPROVED matching confirmation 只允许执行一次
第三次相同写调用重新进入 REQUIRE_CONFIRMATION
```

### 19.10 与真实设备控制的边界

3B-1 不注册新的真实 Write Tool，也不向设备发送任何控制命令。

3B-2 才接第一条真实设备控制能力，并在接入时额外加入：

```text
device allowlist
command allowlist
command id / idempotency
状态校验
执行后审计
```

当前 Slice 3B-1 在本地 Maven、V7 Flyway 和 Confirmation API 验证完成前保持 OPEN。
