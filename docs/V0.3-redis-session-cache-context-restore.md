# V0.3 — Redis Session Cache / Context Restore

## 1. 目标

此前 AgentForge 已经具备：

```text
MySQL
  af_session / af_message
  af_execution / af_trace_event
```

因此“历史事实”不会因 JVM 重启丢失。

但 AgentScope Runtime 过去使用 `InMemoryAgentStateStore`：

```text
JVM restart
  -> AgentState 消失
  -> 相同 sessionId 再请求
  -> 模型不知道重启前的上下文
```

本阶段解决两个问题：

1. 把热 AgentState 放入 Redis，使 JVM 重启后能直接恢复完整 Runtime State。
2. Redis miss 时，从 MySQL Conversation Transcript 重建基本上下文，保证 Redis 不是唯一事实源。

## 2. AgentScope 2.0 StateStore 语义

AgentScope 2.0 的 `AgentStateStore` 以：

```text
(userId, sessionId, key)
```

保存状态。

ReActAgent 的主要状态键是：

```text
agent_state
```

`AgentState` 中包含 conversation context、summary、replyId、tool context 等 Runtime State。

ReActAgent 每次调用都会按 RuntimeContext 的 userId / sessionId 重新从 StateStore 读取状态，并在调用结束后保存状态。

因此最自然的 Context Restore 点不是在 Prompt 前手工拼字符串，而是给 AgentScope 提供正确的 AgentStateStore。

## 3. 为什么没有直接使用新的独立 Redis Client

项目已经通过 Spring Boot / Spring Data Redis 管理 Redis：

```text
spring.data.redis.*
```

本阶段实现 `SpringRedisAgentStateStore`，直接复用 `StringRedisTemplate`。

这样可以：

- 复用现有 Redis 地址、ACL 用户、密码、DB 配置。
- 不额外维护第二套连接池。
- 统一使用 `agentforge:session:` 命名空间。
- 自己定义 TTL 和降级策略。

AgentScope 的 StateStore 接口仍然保持不变，因此 Runtime 层不依赖具体 Redis 客户端。

## 4. Redis Key Namespace

默认：

```text
agentforge:session:
```

而不是 AgentScope 默认命名空间。

这是因为当前 Redis DB 可能与其他服务共享，AgentForge 必须有独立前缀。

单个 Session 的内部 Key 使用：

```text
agentforge:session:u:<encoded-user>:s:<internal-session-id>:state:<encoded-key>
agentforge:session:u:<encoded-user>:s:<internal-session-id>:_keys
```

注意 Runtime 使用的是 MySQL `af_session.id`，不是客户端传入的 external session key。

## 5. TTL

默认：

```text
24h
```

配置：

```text
AGENTFORGE_SESSION_CACHE_TTL
```

Redis Cache 是热状态，不是永久历史库。

Session 持续被使用时，读取/保存会刷新 TTL；冷 Session 最终可以自然淘汰。

永久 Conversation History 仍然在 MySQL。

## 6. Cache Aside + MySQL Fallback

每次 Agent 请求的顺序现在是：

```text
open persistent Session
  ↓
ensureContext()
  ↓
Redis AgentState hit?
  ├─ YES -> 直接使用完整 AgentState
  │
  └─ NO
      ↓
    MySQL af_message
      ↓
    最近 N 条 USER / ASSISTANT
      ↓
    重建 AgentState.context
      ↓
    写回 Redis
  ↓
persist CURRENT USER message
  ↓
AgentScope Runtime
```

特别注意：

```text
ensureContext()
必须发生在
persist CURRENT USER message
之前
```

否则 Redis miss 时从 MySQL 回源会把“本轮 USER Message”也读出来，然后 AgentScope 又会把同一输入追加一次，造成当前消息重复。

这是本阶段最重要的时序约束之一。

## 7. 为什么 MySQL 是 Source of Truth

Redis 丢数据、TTL 到期、重启或换命名空间都不应让 Conversation History 消失。

所以：

```text
MySQL = Durable Conversation Truth
Redis = Hot Runtime State
JVM Memory = Temporary Failure Fallback
```

恢复优先级：

```text
Redis AgentState
   ↓ miss / unavailable
JVM fallback if available
   ↓ miss
MySQL Transcript Hydration
```

Redis 不可用时，`ResilientAgentStateStore` 会把状态临时写入 JVM 内存，使缓存故障不会直接把正常 Agent 请求变成 500。

## 8. MySQL 回源为什么只取最近 N 条

默认：

```text
restore-max-messages = 40
```

不能在一个拥有数千条历史消息的 Session 上：

```sql
SELECT all history
```

然后全部塞进模型 Context。

当前 V1 使用“最近 N 条 Message”作为粗粒度窗口。

它解决数据库和上下文无限增长问题，但还不是最终的 Token-aware Context Window。

后续可演进为：

```text
recent messages
+ conversation summary
+ token budget
+ semantic recall
```

## 9. Redis 命中与 MySQL 回源的保真度不同

Redis 保存的是 AgentScope 完整 `AgentState`，因此可以包含：

- USER / ASSISTANT 上下文
- ToolUseBlock / ToolResultBlock
- summary
- reply/runtime state
- 其他 AgentScope session state

MySQL `af_message` 当前只保存最终 USER / ASSISTANT 对话正文。

因此 Redis miss 后的 MySQL fallback 是：

```text
Conversation Transcript Restore
```

不是：

```text
Exact Runtime Snapshot Restore
```

也就是说，过去 Tool 调用的完整内部 Block 不会从 `af_message` 凭空重建。

这也是为什么 Execution / Trace 和 Conversation 不能混成一张表。

## 10. Context Restore Trace

每次 Execution 开始后会新增：

```text
context_restore
```

content 示例：

```text
source=EMPTY;restoredMessages=0
source=CACHE;restoredMessages=4
source=MYSQL_TRANSCRIPT;restoredMessages=4
```

因此恢复来源本身也进入 Execution Trace，可以做问题诊断和后续指标统计。

## 11. 配置

```yaml
agentforge:
  session-cache:
    enabled: true
    key-prefix: agentforge:session:
    ttl: 24h
    restore-max-messages: 40
```

环境变量：

```text
AGENTFORGE_SESSION_CACHE_ENABLED
AGENTFORGE_SESSION_CACHE_PREFIX
AGENTFORGE_SESSION_CACHE_TTL
AGENTFORGE_CONTEXT_RESTORE_MAX_MESSAGES
```

## 12. 当前边界

1. MySQL fallback 只恢复 USER / ASSISTANT 文本，不恢复完整历史 Tool Blocks。
2. Restore Window 当前按 Message 数量限制，不是按 Token Budget。
3. Redis 与 MySQL 目前采用 cache-aside / eventual consistency，不是分布式强一致事务。
4. Redis 用户索引用于 StateStore 的 listSessionIds 支持，不承担业务事实。
5. Redis 故障时 JVM fallback 只保证当前进程继续工作，进程退出后仍依靠 MySQL 回源。
6. 本阶段恢复“已完成会话上下文”，不解决正在执行到一半时的精确 checkpoint resume。

## 13. 验收步骤

### 13.1 编译测试

```powershell
git pull origin master
git log -1 --oneline
.\scripts\mvn.ps1 clean test
```

要求：

```text
BUILD SUCCESS
```

### 13.2 启动并检查 Health

```powershell
.\scripts\run-dashscope.ps1
```

```powershell
Invoke-RestMethod "http://localhost:8080/api/v1/system/health" |
  ConvertTo-Json -Depth 8
```

重点：

```text
milestone = V0.3-redis-session-cache-context-restore
redis = UP
sessionCacheEnabled = true
sessionCacheTtl = PT24H
contextRestoreMaxMessages = 40
```

本阶段没有新的 MySQL Flyway migration。

### 13.3 新 Session

```powershell
$payload = @{
    userId = "cache-user"
    sessionId = "cache-restore-001"
    message = "Remember the number 7391. Reply exactly: ACK"
} | ConvertTo-Json

$response = Invoke-WebRequest `
    -Method Post `
    -Uri "http://localhost:8080/api/v1/agents/default/stream" `
    -ContentType "application/json; charset=utf-8" `
    -Body $payload `
    -UseBasicParsing

$response.Content
```

第一次应看到：

```text
event:context_restore
source=EMPTY
```

并得到 ACK。

### 13.4 同 JVM Redis Hit

```powershell
$payload = @{
    userId = "cache-user"
    sessionId = "cache-restore-001"
    message = "What number did I ask you to remember? Reply only the number."
} | ConvertTo-Json

$response = Invoke-WebRequest `
    -Method Post `
    -Uri "http://localhost:8080/api/v1/agents/default/stream" `
    -ContentType "application/json; charset=utf-8" `
    -Body $payload `
    -UseBasicParsing

$response.Content
```

预期：

```text
source=CACHE
7391
```

### 13.5 JVM Restart + Redis Restore

停止应用并重新启动：

```text
Ctrl+C
.\scripts\run-dashscope.ps1
```

继续问同一个 Session。

预期仍然：

```text
source=CACHE
7391
```

这证明 Runtime State 已经不依赖旧 JVM 内存。

### 13.6 强制 Redis Miss + MySQL Transcript Restore

停止应用。

临时换一个空 Redis namespace，不删除现有数据：

```powershell
$env:AGENTFORGE_SESSION_CACHE_PREFIX = "agentforge:session:restore-test:"
.\scripts\run-dashscope.ps1
```

继续使用：

```text
userId = cache-user
sessionId = cache-restore-001
```

询问之前记住的数字。

预期：

```text
source=MYSQL_TRANSCRIPT
7391
```

说明即使 Redis 中没有该 Session 的 AgentState，MySQL Conversation 仍能恢复基本上下文。

测试结束后关闭该 PowerShell 或清除临时变量：

```powershell
Remove-Item Env:AGENTFORGE_SESSION_CACHE_PREFIX -ErrorAction SilentlyContinue
```

完成上述三条路径：

```text
EMPTY
CACHE
MYSQL_TRANSCRIPT
```

并验证 JVM restart 后仍可回答历史信息，本阶段才正式关闭。
