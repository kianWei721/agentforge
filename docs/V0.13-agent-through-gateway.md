# V0.13 — Agent Turns Through the Model Gateway (Phase 1)

## 1. 版本目标

V0.9 起知识检索的改写、判定，V0.12 的意图分类都经过模型网关，但 token 花得最多的 Agent 主对话还直连 DashScope。这一版让 Agent 主对话（以及它的压缩摘要）可以按 agent 切到网关：预算、限流、故障切换、数据不出境、调用流水，覆盖到所有对话类调用。

- **按 agent 切换**：agent 定义的 `modelProvider=gateway`、`modelName=<网关路由>` 就走网关；`dashscope` 照旧直连。不改表、不改接口，不用重启（定义的 version 变了，runtime 会换一代）。
- **不悄悄回退**：设成 `gateway` 而网关没开，建 runtime 时直接失败，绝不改走直连。
- 二期（embedding 经网关）等这一期验收后再定；rerank 不走网关，是写明的例外（第 7 节）。

## 2. 怎么接的

```text
AgentScope HarnessAgent ──Model.stream(messages, tools, options)──► GatewayChatModel
    消息转换：AgentScope Msg / ToolSchema ⇄ OpenAI chat（只发网关白名单里的字段）
    ModelGatewayClient.complete：Bearer key、X-Correlation-Id、X-Gateway-Deadline-Ms
                                  ──POST /v1/chat/completions, model=agent──► model-gateway
                                                                                └─ 路由 agent: qwen3.8-flash → qwen-plus
```

- **自己实现 AgentScope 的 `Model`，不加依赖。** 可选的 `agentscope-extensions-model-openai` 会把网关的错误码变成普通 HTTP 异常，而且模型内部自带重试，会把"结果未知、可能已计费"的调用再发一次。自研只用已有的 `ModelGatewayClient`，错误码、请求号、截止时间都沿用 V0.9 的那一套。
- **非流式。** 网关还不支持 `stream=true`，每次调用返回整段回答，不伪造逐字流。HTTP SSE 的首字要等整段生成完；企业微信本来就是拉全量快照，只是回答一次性出现，回合总耗时不变。AgentScope 对整段回答照样产生文本事件（集成测试断言了）。
- **路由 `agent`（model-gateway）**：`[dashscope/qwen3.8-flash, dashscope/qwen-plus]`。只放能通过 OpenAI 兼容协议调用工具的模型，不跨厂商：网关不翻译 Claude 的工具调用，带 tools 的请求会跳过它；一个回合也不该前后由两家厂商的模型回答。`standard` 的首选不支持工具，`rag-json` 是给 JSON 提示词评测过的，都不适合。
- **关联号**：同一回合的所有模型调用（含压缩摘要）共用 `ag-<executionId>`。runtime 写进 Reactor Context，模型从里面读（`ModelCallContext`）。集成测试证实它能穿过 AgentScope 到达模型调用；拿不到时（没有 executionId）每次调用一个随机号。
- **重试**：故障切换是网关的事。`GatewayChatModel` 只对什么都不可能已计费的错误（`RATE_LIMITED`、`NO_UPSTREAM_AVAILABLE`、`GATEWAY_UNREACHABLE`）补一次，而且第一次失败时还剩超时的一半以上；重试只用剩下的时间，一次模型调用连重试在内不超过 `agent-request-timeout`。`UPSTREAM_OUTCOME_UNKNOWN`、`GATEWAY_TIMEOUT` 绝不重发。直连模型原本最多自动重试 3 次，这层没有了，偶发错误更容易被用户看到。
- **框架会把失败的调用再发一次，这里拦住了。** 本地验证时发现：AgentScope 2.0.0 的压缩中间件（`CompactionMiddleware`）把"压缩"和"推理"放在同一条链上、用同一个错误处理，模型调用一失败，它记一句 "Compaction failed, continuing without compaction"，然后把推理再跑一遍，于是同一个请求被发了第二次——包括"结果未知、可能已计费"的那种（直连路径也一样，只是直连模型自己还会再重试）。所以同一个回合里（同一个 `ag-<executionId>`）、请求体完全相同的调用失败过一次，再来就直接抛同一个失败，不再发出；集成测试 `aFailedCallIsNotSentAgainWhenAgentScopeRepeatsTheReasoningStep` 断言 AgentScope 问了两次、网关只收到一次。记忆按回合和请求体摘要存，最多 1000 条、5 分钟。
- **回合被取消时**（网页断开、企业微信回合超时），正在退避或阻塞的调用被中断后直接结束，不再把错误抛给已经没人等的下游。
- **`max_tokens` 每次都发**（默认 2048，调用方要得更少就取更少）：网关按它预占预算。单次调用超时默认 40 秒，网关自己 45 秒封顶。
- **并行工具调用关闭**（`parallel_tool_calls=false`），和直连时一样一次一个：工具治理和检索预算按调用顺序计数。

## 3. 消息转换

| AgentScope | OpenAI chat |
|---|---|
| SYSTEM / USER 的文本、提示块 | `system` / `user`，`content` 为文本 |
| ASSISTANT 的文本 + `ToolUseBlock` | `assistant`，`content`（没有文本时为 null）+ `tool_calls[{id, function{name, arguments}}]`，`arguments` 优先用模型给的原文 |
| `ToolResultBlock`（TOOL 消息里；AgentScope 2.0.0 的 USER 消息不能带它） | 每个结果一条 `tool` 消息，`tool_call_id` 原样带回，内容是文本 |
| 思考块 | 丢掉，思考开不开由网关按模型配置 |
| 图片、音频、视频、数据块 | 直接失败（`UNSUPPORTED_CONTENT`），不当成别的东西发出去；工具结果里的这类块写成"[ImageBlock omitted]" |
| 响应 `tool_calls` | 每个一个 `ToolUseBlock`；`arguments` 不是合法 JSON 时 input 为空，由工具报参数错误，回合不在这里失败（原文只留在这次响应上，进入历史后 AgentScope 会换成 `{}`） |
| 响应 `finish_reason=length` | 回答被 `max_tokens` 截断：记一条 WARN，带网关请求号和关联号 |
| 响应 `usage` | `ChatUsage`（含 `cached_tokens`）；网关请求号和实际服务的模型放进 metadata |

**调用和结果必须成对。** 压缩可能把一对调用和结果切开，等待人工确认（挂起）的调用也没有结果；OpenAI 兼容接口遇到会直接 400，整个回合失败。所以发送前只保留有结果的调用和有调用的结果，丢弃的数量记 WARN。

## 4. 切换企业微信的 agent

现有的更新接口是**整体覆盖**：没带的字段会被重置成默认值（提示词变成默认提示词，工具清空）。所以先取回当前定义，只改两个模型字段，其余原样带回：

```bash
curl -s localhost:8080/api/v1/agents/wecom-assistant -H "X-AgentForge-User-Id: <staff user>"
```

```bash
curl -X PUT localhost:8080/api/v1/agents/wecom-assistant -H "X-AgentForge-User-Id: <staff user>" -H "Content-Type: application/json" --data-binary @agent.json
```

`agent.json` 是上一步取回的 `name`、`description`、`systemPrompt`、`toolNames`、`enabled`，加上 `"modelProvider":"gateway","modelName":"agent"`。回滚同样操作，改回 `"modelProvider":"dashscope","modelName":"qwen3.8-flash"`。

前提：

- `agentforge.model-gateway.enabled=true`。**如果部署时网关原本是关的，打开它要重启，而且会同时把知识检索的查询改写和可答性判定切到网关**（V0.9 的行为，不能只切 Agent）；网关已经开着时，切 agent 不用重启。
- AgentForge 用的调用方 key 包含 `agent` 路由。网关的 key 签发时就定死了路由，要重新签一把（`routes=[rag-json, standard, light, agent]`）替换 `AGENTFORGE_MODEL_GATEWAY_API_KEY`。

## 5. 配置

```yaml
agentforge:
  model-gateway:
    enabled: true
    agent-max-tokens: 2048        # AGENTFORGE_MODEL_GATEWAY_AGENT_MAX_TOKENS
    agent-request-timeout: 40s    # AGENTFORGE_MODEL_GATEWAY_AGENT_REQUEST_TIMEOUT
```

## 6. 测试与验证

**每次构建都跑：**

| 测试 | 证明什么 |

| `GatewayAgentTurnTest` | 真实 HarnessAgent + 假网关（先要求调工具，再回答）+ 一个工具：工具按模型给的参数执行；回答作为消息块到达流里；两次模型调用都带 `ag-exec-1`；第二次调用带上了工具结果 |
| `GatewayAgentTurnTest.aFailedCallIsNotSentAgainWhenAgentScopeRepeatsTheReasoningStep` | 网关回"结果未知"时整个回合失败；AgentScope 调了模型两次，网关只收到一次请求 |

| model-gateway `DemoCatalogTest` | 发布的 `agent` 路由只有支持工具的 DashScope 模型 |

**真实冒烟（按需，花钱）：** `GatewayAgentSmokeTest`，`-Dagentforge.agent.smoke=true`。真实 HarnessAgent、内存 state store、两个不依赖 ES 的假工具（查订单、查发票），不连 MySQL、Redis、ES。同样 11 个回合分别经网关（`agent` 路由）和直连 DashScope（`qwen3.8-flash`）各跑一遍，报告见 [docs/eval/V0.13-agent-gateway-smoke-2026-10-25.md](eval/V0.13-agent-gateway-smoke-2026-10-25.md)：

| 路径 | 回合 | 通过 | 工具调用正确 | 错误 | 中位耗时 | 最长 |
|---|---|---|---|---|---|---|
| 经网关 | 11 | 11 | 11 | 0 | 1649 ms | 2853 ms |
| 直连 | 11 | 11 | 11 | 0 | 2496 ms | 5156 ms |

覆盖：单工具、两个工具同一回合、查无此单、没有单号先追问、不该调工具的寒暄和超范围问题、同一会话的追问（第二轮只说"那 B2 呢"，靠历史接上）。网关侧 20 次调用全部成功、都由 `qwen3.8-flash` 服务，共 ¥0.0041；"两个工具"那个回合的 3 次调用在流水里按 `ag-smoke-…-gateway-two-tools-0` 一次查出，抽查这 3 条都是 `model_check=MATCH`。经网关更快，推测是网关给 qwen3.8-flash 关了思考；11 个回合只能看方向。

那次运行比较工具调用时先去了重：同一个工具同样的参数调两次也会被算作正确（之后已改成不去重）。网关这边可以从调用次数反推没有重复：7 个单工具回合各 2 次、两个工具的回合 3 次、3 个不调工具的回合各 1 次，正好 20 次。直连路径不经过网关，没法这样核对。

**本地环境里切换企业微信 agent（2026-10-25）：** 用仓库的 `docker-compose.yml` 在本机起了全新的 MySQL 8.4 和 Redis 7.4（不连任何共享环境），Flyway 在空库里执行了 V1–V12；按第 4 节先取回定义、再整体提交，把企业微信 agent 从 `dashscope/qwen3.8-flash`（v1）切到 `gateway/agent`（v2），提示词和工具都保留。之后用一个模拟企业微信的客户端发加密回调：

- 切换前的消息走直连，切换后的消息走网关 `agent` 路由，入站表和网关流水都对得上，网关按 `ag-<executionId>` 一次查出这一回合的全部调用。
- 但这时百炼账号的免费额度用完了（开着"仅使用免费额度"），直连和网关都被百炼以 403 `AllocationQuota.FreeTierOnly` 拒绝：切换后企业微信收到"模型服务繁忙，请稍后再试（请求号 req-…）"，入站表记 `MODEL_NO_UPSTREAM_AVAILABLE`，网关流水里两个候选都是 `UPSTREAM_REJECTED`、费用 0。**所以企业微信渠道经网关"成功回答"这一步还没在真实环境跑通**，成功路径只由第 6 节的冒烟（不经企业微信渠道）证明。
- 上面那条框架重发的问题就是在这一步发现的：一个回合在网关流水里出现了 4 次请求（自己的 1 次重试 × 框架的 1 次重跑），修复后同样的场景只剩自己的那次重试。

## 7. 已知限制与没做的事

- **rerank 仍直连 DashScope，是写明的例外。** 默认关闭，没有 OpenAI 标准接口，单独做一套不值得。生产开 rerank、或对账发现绕过网关的费用不可忽略时再做。
- **embedding 仍直连**（二期）。
- **没有流式**：网页首字慢；网关 45 秒单次上限，长回答会失败。网页成为主要入口、首字延迟进验收，或超时失败率超过 1% 时，再给网关补流式。
- **失去直连模型内部的 3 次重试**，只剩网关的故障切换和一次受限重试。
- **没有回合剩余时间传给网关**：单次调用的截止时间只看 `agent-request-timeout`；企业微信回合超时时外层会取消，但已经发出的阻塞请求要等网关自己的截止时间才放弃。
- **网关成为所有模型调用的单点**，网关是单实例；Agent、知识检索、意图分类共用同一个团队的日预算，`BUDGET_EXCEEDED` 会让它们一起停，key 的每分钟上限要按一个回合 3–6 次调用来定。
- **一个回合里可能降级到 qwen-plus**，前后轮由不同模型回答；qwen-plus 在 `agent` 路由上还没用 Agent 的工具冒烟过（冒烟的 20 次调用全由 qwen3.8-flash 服务）。
- **`max_tokens` 固定上限 2048**：直连原来不发，现在超长回答或超长的工具参数会被截断，只有一条 WARN，用户看到的是半截回答。
- 冒烟里有一个回合的回答以一句英文开头（"I'll check both for you now."，模型在调工具前说的话），直连没有出现；样本太少，记下待观察。
- HTTP 的 `/api/v1/agent/stream` 没有把网关错误映射成带错误码的 SSE 事件（已有问题，补它属于对外 SSE 契约变更）。
- 压缩摘要在非流式下省不了 token（`SummaryLengthLimitedModel` 是在输出端截断，整段已经生成）。
