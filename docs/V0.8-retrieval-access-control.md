# V0.8 — Retrieval Access Control

## 1. 版本目标

同一个知识库，员工能看到的和客户能看到的是两套边界。V0.8 要保证：**这条边界在检索层和数据层执行，不靠提示词约束。**

具体验收口径：

- 客户 A 无论怎么提问，都检索不到客户 B 的文档和内部文档；
- 越权的 chunk 不会进入 rerank 和 answerability judge，这两步都是外部 LLM 调用；
- 删除或停用的文档立即不可见，不需要等索引重建；
- 绕开检索的其他入口（文档 API、执行轨迹、会话历史）不能读到同样的内容。

## 2. 权限模型

文档级 ACL，chunk 继承所属文档：

| visibility | 谁能读 |
|---|---|
| `INTERNAL` | 仅员工。迁移后存量文档的默认值 |
| `PUBLIC` | 所有已登记的员工和客户 |
| `CUSTOMER` + `customerId` | 员工，以及这一个客户 |

身份只有两类：`STAFF`、`CUSTOMER(customerId)`。"员工只能看自己负责的客户"不在本版范围，见第 7 节。

`KnowledgeAccessPolicy.permits` 是唯一的权限定义。ES 过滤条件、SQL 谓词、检索后守卫都是它的翻译，并且都由 `unrestrictedVisibilities` 和 `customerScope` 这两个构件拼出来，避免三处各写一套逻辑、悄悄出现分歧。

## 3. 四道关

```text
请求 ──► ① 身份入口 ──► ② 检索前置过滤 ──► ③ MySQL 回查守卫 ──► RRF ──► rerank / judge (LLM)
                                                              ▲
         ④ 绕开检索的入口：文档 API / traces / 会话 ─────────────┘ 同一套 permits / 归属校验
```

**① 身份入口**（`TrustedIdentityWebFilter`）
`/api/v1/**` 除 health 外，一律从网关注入的 `X-AgentForge-User-Id` 取用户，再经服务端 `PrincipalDirectory` 解析成主体。未知用户返回 401。Controller 通过参数注入拿到 `AccessPrincipal`，请求体和 query 里的 userId 全部删掉。Agent 工具从 `ToolInvocationContext.userId` 解析身份；工具 schema 只有 `query/topK`，并且 `additionalProperties=false`，**模型没有任何途径传身份进来**。

**② 检索前置过滤**（`ElasticsearchKnowledgeSearchBackend`、`JdbcKnowledgeRepository`）

- BM25：`bool.must[multi_match] + bool.filter[acl]`
- ES 8 kNN：`knn.filter` 在 ANN 搜索过程中生效，k 统计的是可读的 chunk。不用顶层 `post_filter`，因为它在选出 k 个近邻之后才过滤，会把客户的结果削空。
- ES 7：`script_score.query` 由 `match_all` 换成 `bool.filter[acl]`
- MySQL 兜底检索：`WHERE` 先过滤再 `LIMIT`
- 员工身份同样显式带上 `terms visibility ∈ {INTERNAL, PUBLIC, CUSTOMER}`，而不是不加过滤。迁移后如果没重建索引，缺少 ACL 字段的旧 chunk 对任何人都不可见（fail-closed）。

**③ MySQL 回查守卫**（`KnowledgeAccessGuard`）
ES 返回结果后、进入 RRF 之前，拿命中的 documentId 回查 `af_knowledge_document` 当前的 `enabled` 和 ACL，不可读的直接丢弃。原因有两个：

- 索引是派生数据。删除、停用、改 ACL 之后，在重建之前它都是旧的。
- ES 过滤条件是一段翻译，翻译本身也可能写错。

只复核 ES 命中里自带的 ACL 字段没有意义，因为那和过滤用的是同一份数据。丢弃条数记在 `accessDiagnostics.guardDroppedHits`，正常应为 0；不为 0 说明索引过期或过滤有 bug。

**④ 其他入口**

- 文档 API：读接口按 `permits` 过滤，不可读与不存在返回同样的错误，防止拿 id 探测；创建、删除、重建索引、评测仅限员工。
- `/executions/{id}`、`/traces`：只有本人可读。trace 里有工具返回的原文，包括检索到的 chunk。
- 会话和 tool confirmation：userId 一律取自身份入口。

## 4. 数据迁移

`V10__add_knowledge_document_access_scope.sql`：

- `visibility VARCHAR(16) NOT NULL DEFAULT 'INTERNAL'`
- `customer_id VARCHAR(64) NULL`
- `CHECK`：`CUSTOMER` ⇔ `customer_id` 非空
- 索引 `(visibility, customer_id)`

上线顺序：执行迁移 → 把需要公开或归属客户的文档改掉 → `POST /api/v1/knowledge/index/rebuild`。重建之前，旧索引里的 chunk 因为缺少 ACL 字段，对所有人都不可见。

## 5. 配置

```text
AGENTFORGE_STAFF_USER_IDS=dev-staff
AGENTFORGE_CUSTOMER_USERS=demo-customer-a=cust-a,demo-customer-b=cust-b
```

启动时校验：同一个用户同时出现在员工和客户里、格式错误、空 id，都会直接启动失败。身份有歧义时，绝不能悄悄落到权限更大的一边。两个变量都没有默认值。

`scripts/` 下的脚本默认以 `dev-staff` 身份调用，可以用 `-UserId` 或 `AGENTFORGE_SCRIPT_USER_ID` 覆盖。

## 7. 已知限制与没做的事

- **没有在真实 ES 上验证 top-k 削空现象。** 单测只断言请求体结构；`knn.filter` 和 `post_filter` 的行为差异来自 ES 文档，没有在本项目里实测过。
- **app 层没有自动化测试**（WebFilter、参数注入、各 controller 的归属校验）。只做了编译验证，没有启动应用跑过。
- 身份 header 是否可信，取决于部署契约：网关必须剥掉客户端自带的 header，应用不能被直连。本项目不包含网关。
- 员工可以看全部知识，没有"只看自己负责的客户"这一层行级隔离。如果要做，`AccessPrincipal` 需要带上客户集合，三处翻译都要同步扩展。
- 删除文档不会同步删除 ES 里的 chunk，靠守卫保证不可见；索引里会留着死数据，直到下次重建。
