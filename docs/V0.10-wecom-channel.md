# V0.10 — WeCom Channel and Session Isolation

## 1. 版本目标

企业微信里的同事和客户直接 @ 机器人提问，AgentForge 的 Agent 来回答。要守住三条边界：

- 每个人、每个群的对话互不串：上下文、记忆、执行记录都分开；
- 群里的回答全群可见，检索身份不能按"谁提的问题"来定；
- 企业微信重复投递、并发提问时，同一条消息只跑一次，同一会话不会两个回合同时跑。

渠道选的是企业微信**智能机器人 + HTTP 回调**：

- 自建应用收不到群聊消息；
- 长连接协议只在官方 SDK 源码里出现，没有协议文档；HTTP 回调的加解密有官方文档，能用官方样例验证。

## 2. 一条消息怎么走

```text
企业微信 ──POST /callbacks/wecom/bot──► 验签 + 时间戳窗口 + 解密
  同步段（目标 200ms 内，企业微信 5 秒收不到应答就重试）：
    ① 路由：会话类型、消息类型、Agent 工具白名单、单聊映射 / 群绑定 → 服务端派生会话键
    ② INSERT af_channel_inbound；唯一键冲突 = 重复投递 → 返回同一个流的当前内容
    ③ 拒绝的消息：固定文案，finish=true，不启动 Agent
    ④ 接受的消息：交给会话串行门，先回 stream{id, finish:false}
  异步段（worker 池）：
    排队过了企业微信的窗口 → 记 EXPIRED_IN_QUEUE，不调用 Agent
    再查一次工具白名单 → AgentConversationRuntimeService（source=wecom）
    → 文本增量写入流缓存 → 入站表写 DONE / FAILED → 流标记结束
企业微信 ──流式刷新回调（同一个 stream.id）──► 返回当前全量内容，直到 finish=true
```

流式回复是**拉**的：企业微信按 stream.id 来刷新，每次回复覆盖上一次显示的内容，所以返回的总是全量快照，不是增量。

## 3. 会话隔离

| 场景 | 以谁的身份运行 | 会话键 |
|---|---|---|
| 单聊 | 企微 userid 经配置映射成 AgentForge 用户，再走 `PrincipalDirectory` | `wecom:` + sha256(机器人, 单聊, userid) |
| 群聊 | 群绑定的合成用户 `wecom-group:*`（登记为客户身份） | `wecom:` + sha256(机器人, 群, chatid) |

几个关键取舍：

- **群按群的身份检索，不按提问人。** 回答对全群可见；按提问人的权限检索，员工在客户群里一问，内部文档就会贴给客户。检索层 ACL（V0.8）照常生效，prompt 改变不了身份。
- **员工群默认禁用。** 企业微信不会通知成员变动，员工群混进外部联系人后，内部文档就外泄了。需要时用 `allow-staff-groups` 显式打开。
- **群绑定合成用户，不绑真人。** 绑真人的话，这个人能通过 HTTP API 读写群会话。合成用户以 `wecom-group:` 开头，`TrustedIdentityWebFilter` 拒绝这个前缀，所以没有人能以群的身份登录。换绑会换 user_id，旧上下文自然断开。
- **会话键做哈希。** `af_session.session_key` 用的是不区分大小写和重音的排序规则，而企微 id 区分大小写，用原始 id 会让两个群共用一个会话。
- **渠道会话只有一个写入口。** 检查放在 `AgentConversationRuntimeService` 里，所有 HTTP 入口（包括旧的 `/api/v1/agent/stream`）都经过它。前缀判断不区分大小写，打开会话后还会用数据库实际存的 key 再判断一次，所以 `WECOM:…`、`wécom:…` 这类写法也写不进渠道会话。HTTP 只能读。
- **只认 `single` 和 `group` 两种会话类型。** 缺字段或出现未知值一律拒绝，不会默认当成单聊，用某个员工的权限在别人能看到的地方回答。
- 发言人只记在入站表里，不注入 prompt。
- 非文本消息、空消息直接拒绝。

## 4. 工具：白名单代替"逐个拒绝"

渠道绑定一个专用 agent，并配置工具白名单（默认只有 `search_knowledge`：只读，而且有检索层 ACL）。

为什么不只拒绝"需要确认"的工具：设备类工具不按身份过滤，工具策略关闭时还会全部放行，所以客户群照样能查任意设备。用白名单之后，人工确认（HITL）的问题也不存在了：需要确认的工具根本进不了渠道。

白名单**检查两次**：消息到达时一次，回合真正执行前再一次。排队期间管理员给 agent 加了白名单外的工具，执行前会被拦下，记 `AGENT_TOOLS_NOT_ALLOWED`。

## 5. 去重、串行、超时

**去重：** 用 `af_channel_inbound` 的唯一键 `(channel, bot_id, msg_id)`，msg_id 用 utf8mb4_bin。

- 不用 Redis：Redis 不可用时会退到 JVM 兜底，去重就悄悄失效了。数据库唯一键和实例数量无关。
- 流 id 由 msg_id 派生，重复投递拿到的是同一个流。
- 重试有可能比原请求先拿到结果（原请求的插入很慢，被企业微信断开后重试）。这时流还没建好，重复投递返回空内容和 `finish=false`，让企业微信继续刷新，不会把回复提前结束掉。

**串行（`SessionTurnGate`）：**

- 同一会话先进先出，不同会话在固定 worker 池里并行（默认并发 4，全局排队 64）。
- 每个会话最多 1 条在跑、3 条排队，超出时回"前面的问题还在处理中"，全局排满回"咨询的人比较多"。
  - 单聊时这和企业微信"同一用户最多 3 条消息同时交互"差不多。
  - 群会话是多人共用的，企业微信的单用户限制管不到它，起作用的是这个排队上限。
- 出错的回合也会释放会话。

**超时按企业微信的窗口算，并且是总时长：**

- 企业微信从用户发消息起最多刷新 6 分钟。截止时间从**收到消息**的时刻起算，留 20 秒余量，即 5 分 40 秒；排队的时间也算在里面。
- 排到时已经过了截止时间，直接记 `EXPIRED_IN_QUEUE`，不调用 Agent，不花模型费用，也不往会话里写一条用户看不到的回答。
- 实际超时取 `turn-timeout`（默认 5 分钟）和剩余时间的较小值。
- 超时加在**完成信号**上（`.then().timeout(...)`），不是 `Flux.timeout`：后者只限制两次输出之间的间隔，一个不停输出的 ReAct 回合永远不会超时。
- `stream-ttl` 校验为不短于 6 分钟，回复在企业微信还可能拉取的整个时间里都能读到。

**并行的前提**（读 AgentScope 2.0.0 字节码确认）：同一个 agent 实例按 `(userId, sessionId)` 分槽，`callSerializationKey`、每会话的 `stateCache` 都是这样。共享的 `activeRc` 字段没有被任何内部代码读取。AgentForge 的工具是从每次调用的参数里拿运行上下文，不读 agent 级的共享字段。

**失败和收尾：**

- 模型网关的错误显示为"模型服务繁忙…（请求号 gw-…）"，入站表记 `MODEL_<code>`；超时记 `TURN_TIMEOUT`。
- 已经显示出来的部分回答会保留；失败提示总是可见，回答超长被截断时也会给提示留出位置。
- 先写入站表，再把流标记为结束。写库本身失败时只记日志，用户看到的结果不受影响。
- 流缓存里的文本、失败提示和"已结束"标志在同一把锁里修改和读取，快照不会出现"已结束"却缺最后一段的情况。

## 6. 加解密

- 签名：token、timestamp、nonce、密文按字典序拼接后做 sha1，用常量时间比较。
- 时间戳必须在 ±5 分钟内，防重放。
- AES-256-CBC，IV 取 key 的前 16 字节。
- **企业微信按 32 字节做 PKCS#7 填充，JDK 的 `PKCS5Padding` 解不开**，所以用 `NoPadding` 手动去填充。测试里专门断言了 JDK 填充会抛 `BadPaddingException`。
- 回调路径在 `/api/v1` 之外：企业微信不带身份头，验签就是鉴权。验签或解密失败时返回 403 和空 body。
- 配置了 `receive-id` 时，用别的接收方加密的消息在解密这一步就会被拒（403）。`receive-id` 默认留空，这时靠 `aibotid` 和配置的 bot-id 比对来拦，返回的是拒绝文案（`BOT_MISMATCH`），不是 403。

## 7. 配置

```yaml
agentforge:
  channel:
    wecom:
      enabled: true                      # 需要 agentforge.agent.enabled=true，否则启动失败
      token: ...
      encoding-aes-key: ...              # 43 位
      receive-id: ""                     # 留空则不校验，见第 6、9 节
      bot-id: ...
      agent-id: wecom-assistant
      allowed-tools: search_knowledge
      direct-users: zhangsan=dev-staff
      groups: wrkXXXX=wecom-group:cust-a # 同时在 customer-users 登记 wecom-group:cust-a=cust-a
      allow-staff-groups: false
      turn-timeout: 5m                   # 必须短于 6 分钟；实际还受第 5 节的截止时间约束
      stream-ttl: 10m                    # 不能短于 6 分钟
```

## 9. 已知限制与没做的事

- **没有和真实的企业微信联调过。** 加解密由官方样例验证；端到端靠测试里的模拟器。
- **回包信封的字段名没有在官方文档里核实**（`encrypt`、`msgsignature`、`timestamp`、`nonce`，以及 timestamp 是数字还是字符串），参照的是 SDK 和第三方资料。智能机器人解密时的 receiveid 取值也没查到，所以做成了可配置、可留空。
- **`from.userid` 只有在机器人创建者是超级管理员时才是明文**，否则是加密 ID。映射配置要按实际收到的值来写。
- **V11 没在 MySQL 上执行过。** 本机没有 MySQL；仓储测试用的是手写的 H2 建表语句，"msg_id 区分大小写"验证的是 H2 的默认行为，不是 `utf8mb4_bin`。
- **超时取消之后，AgentScope 正在进行的模型或工具调用是否真的停了，没有验证。** 串行门在超时后会放行同一会话的下一个回合；如果上游没有响应取消，两个回合可能短暂重叠。HTTP 客户端断开时也是同样的取消路径。
- **白名单复查后还有毫秒级的窗口**：复查和 runtime 读取 agent 定义是两次查询，中间改了 agent 仍可能漏过。要完全封住，需要 runtime 按请求携带的允许工具集合来构建回合。
- **单实例。** 串行门和流缓存都在 JVM 里；多实例部署要改成 Redis 锁加共享缓存，或者按会话路由。
- **崩溃窗口。** 入站表已插入、回合还没跑完时进程崩溃，这条消息会停在 RECEIVED 状态，没有补偿重放；企业微信后续的刷新会拿到"已过期"。
- **HTTP 入口自己的同会话并发**这次没修：串行门只管企业微信渠道。
- **app 层的 Controller 和身份过滤器没有自动化测试**（回调 Controller、`wecom-group:` 前缀拒绝），只做了编译验证。渠道会话的写入限制在 runtime 层，有测试覆盖。
- 没做：非文本消息、模板卡片、回复确认码审批写操作、群成员同步、对账任务、映射配置入库。
