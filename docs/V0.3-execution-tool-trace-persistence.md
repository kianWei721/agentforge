# V0.3 — Execution / Tool Trace Persistence

## 目标

Session / Message Persistence 解决“用户和 Agent 说了什么”。本阶段解决另一类问题：一次 Agent 请求内部到底发生了什么。

需要能够回答：

- 这次执行何时开始、何时结束、最终状态是什么。
- 调用了几次模型。
- 是否调用 Tool，调用了哪个 Tool。
- Tool 参数和返回结果是什么。
- 一次 Tool Call 与 Tool Result 如何关联。
- 模型调用消耗了多少 Token、耗时多少。
- 哪一步失败。

## 数据职责

Conversation 与 Execution 分开建模：

```text
Conversation
= 用户可见的对话事实

Execution / Trace
= Agent 内部执行事实
```

因此 Tool Call、Tool Result、Model Usage 不写入 `af_message`。

## 数据模型

`af_execution` 表示一次 Agent 请求的执行摘要：

```text
id
session_id
agent_id
user_id
user_message_id
assistant_message_id
model_provider
model_name
status
started_at
completed_at
duration_ms
error_type
error_message
```

状态机：

```text
RUNNING
  -> SUCCEEDED
  -> FAILED
  -> CANCELLED
```

`af_trace_event` 表示执行过程中的有序事件：

```text
execution_start
model_call_start
tool_call_start
tool_call_delta
tool_call_end
model_call_end
tool_result_start
tool_result_delta
tool_result_end
...
```

实际顺序由 AgentScope 的 ReAct 循环决定，业务代码不假设固定事件序列。

## 为什么 Execution 与 Trace 分表

Execution 是一次运行的摘要；Trace 是这次运行内部的事件明细。

```text
af_execution 1 ---- N af_trace_event
```

如果全部放在一张表，每个事件都要重复 Agent、User、Model、Status 等字段，而且查询“最近执行是否成功”也会变得笨重。

## Trace 顺序

时间戳不能提供严格全序关系，所以每个 Execution 保存 `next_trace_sequence`。

追加事件时：

```sql
SELECT next_trace_sequence
FROM af_execution
WHERE id = ?
FOR UPDATE;
```

拿到序号后写入 `af_trace_event.sequence_no`，再递增 `next_trace_sequence`。

这和 Message Persistence 的设计一致：顺序是业务事实，不依赖时间戳猜测。

## replyId 与 toolCallId

AgentScope 事件使用两个重要 Correlation ID（关联 ID）：

- `replyId`：关联同一次回复中的模型推理事件。
- `toolCallId`：关联一次 Tool Call 与对应 Tool Result。

Tool 参数是流式生成的，因此本阶段新增 `tool_call_delta`，把 JSON 参数片段保存到 Trace。

Tool Result 的文本增量保存为 `tool_result_delta`。

这使执行过程能够按 `sequence_no` 重放，而不是只留下最终答案。

## Model Usage

AgentScope `ChatUsage` 提供：

```text
inputTokens
outputTokens
cachedTokens
time
```

本阶段结构化保存为：

```text
input_tokens
output_tokens
cached_tokens
model_time_ms
```

不再把 Java 对象的 `toString()` 当 Usage 数据。

后续可以直接计算 Agent / Session 的 Token 成本、模型耗时和 P95/P99 等指标。

## WebFlux 与 JDBC

Trace Persistence 使用阻塞 JDBC，不能直接阻塞 Netty Event Loop。

当前使用：

```text
concatMap + boundedElastic
```

`boundedElastic` 隔离阻塞数据库访问，`concatMap` 保持 Trace 写入顺序。

当前采取 correctness-first（正确性优先）：每个 Trace Event 都立即持久化。代价是 Tool 参数或 Tool Result 很长时会产生更多数据库往返。

后续高吞吐阶段可以演进为批量缓冲、异步 Trace Sink 或消息队列。

## durable done

SSE 的 `done` 现在具有更严格的语义：

```text
模型流结束
  -> 保存 ASSISTANT Message
  -> af_execution = SUCCEEDED
  -> 最后发送 done
```

这样客户端收到 `done` 后立刻查询 Execution，不会因为持久化尚未完成而仍看到 RUNNING。

## 错误与取消

正常结束：

```text
RUNNING -> SUCCEEDED
```

模型、Tool 或 Trace 链路异常：

```text
RUNNING -> FAILED
```

客户端取消 SSE：

```text
RUNNING -> CANCELLED
```

如果“写入 FAILED 状态”本身失败，系统保留原始业务异常，不用二次持久化错误覆盖真正的根因。

## 当前边界

- Trace API 暂未分页。
- Tool Delta 当前逐事件写库，写放大尚未优化。
- 进程异常退出时可能留下 RUNNING Execution。
- 多实例环境不能简单在应用启动时把所有 RUNNING 改成失败，否则可能误伤其他实例仍在执行的请求；后续需要 instance ownership、heartbeat 或 lease。
- Execution Persistence 不等于 Context Restore；AgentScope 仍使用 InMemoryAgentStateStore。

## API

```http
GET /api/v1/executions/{executionId}
GET /api/v1/executions/{executionId}/traces
GET /api/v1/agents/{agentId}/sessions/{sessionId}/executions?userId={userId}
```

SSE 开始时新增：

```text
event:execution_start
metadata.executionId = ...
```

客户端可以用这个 ID 把实时流与持久化 Execution 精确关联。

## 验收

先执行：

```powershell
git pull origin master
.\scripts\mvn.ps1 clean test
.\scripts\run-dashscope.ps1
```

Flyway 应执行：

```text
V3__create_execution_trace_tables.sql
```

数据库新增：

```text
af_execution
af_trace_event
```

使用 Tool Calling 验证：

```powershell
$payload = @{
    userId = "trace-user"
    sessionId = "trace-verify-001"
    message = "Use query_device_status to check device 367. You must call the tool and then answer with the result."
} | ConvertTo-Json

$response = Invoke-WebRequest `
    -Method Post `
    -Uri "http://localhost:8080/api/v1/agents/default/stream" `
    -ContentType "application/json; charset=utf-8" `
    -Body $payload `
    -UseBasicParsing

$response.Content
```

从 SSE 提取：

```powershell
$response.Content -match '"executionId":"([^"]+)"' | Out-Null
$executionId = $Matches[1]
$executionId
```

查询执行：

```powershell
Invoke-RestMethod "http://localhost:8080/api/v1/executions/$executionId" |
  ConvertTo-Json -Depth 8
```

查询 Trace：

```powershell
Invoke-RestMethod "http://localhost:8080/api/v1/executions/$executionId/traces" |
  ConvertTo-Json -Depth 8
```

验收重点：

```text
Execution.status = SUCCEEDED
assistantMessageId != null
durationMs >= 0

Trace 中存在：
execution_start
model_call_start / model_call_end
tool_call_start / tool_call_delta / tool_call_end
tool_result_start / tool_result_delta / tool_result_end

toolName = query_device_status
同一次调用的 toolCallId 能贯穿 call/result
tool_result_end.state = SUCCESS
model_call_end 存在 inputTokens / outputTokens
```

完成上述验证后，本阶段才正式关闭。
