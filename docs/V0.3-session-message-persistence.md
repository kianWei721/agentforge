# V0.3 — Session / Message Persistence

## 1. Problem

V0.2 的 AgentScope 已经能使用 `userId + sessionId` 做运行期多轮对话，但状态存放在 `InMemoryAgentStateStore`。

这意味着：

- JVM 重启后，平台无法查询历史 Session。
- 前端无法展示稳定的历史对话。
- 后续做审计、Trace、Token 成本分析时没有稳定的会话主键。
- 不同 Agent / User 如果使用相同外部 sessionId，缺少平台级持久化身份边界。

本阶段把“运行时会话”提升为“平台领域对象”。

## 2. Domain boundary

新增独立模块：

```text
agentforge-conversation
```

该模块只定义：

- `ConversationSession`
- `ConversationMessage`
- `ConversationRole`
- `ConversationRepository`
- `ConversationService`

它不依赖 JDBC、Spring Data、MySQL 或 AgentScope。

MySQL 实现放在：

```text
agentforge-infrastructure
  -> JdbcConversationRepository
```

这保持了领域接口与基础设施实现的依赖方向。

## 3. Session identity

外部请求仍使用：

```text
agentId + userId + sessionId
```

数据库用唯一键：

```text
(agent_id, user_id, session_key)
```

平台另外生成内部 `af_session.id`。

AgentScope RuntimeContext 使用这个内部 ID 作为真正的 runtime sessionId。

这样可以避免：

```text
agent-A / user-1 / session-001
agent-B / user-1 / session-001
agent-A / user-2 / session-001
```

因为外部 sessionId 相同而共享运行时状态。

## 4. Message ordering

不能依赖 `created_at` 保证消息顺序。

同一微秒内可以写入多条消息，多实例并发时机器时间也不是可靠的全序关系。

因此 `af_session` 保存：

```text
next_sequence
```

追加消息时事务执行：

```sql
SELECT next_sequence
FROM af_session
WHERE id = ?
FOR UPDATE;
```

然后插入：

```text
sequence_no = next_sequence
```

最后递增 `next_sequence`。

这给同一个 Session 建立数据库级单调序列。

## 5. Streaming persistence

SSE 输出是很多 delta：

```text
"Device"
" 367"
" — Status"
" ONLINE"
```

如果每个 delta 都写一条数据库记录，历史消息会碎裂，写放大也很严重。

因此本阶段：

1. USER 请求进入 Agent 前写一条 USER Message。
2. ASSISTANT 的 SSE delta 在内存中拼接。
3. Agent Stream 正常完成后只写一条 ASSISTANT Message。

Tool Call / Tool Result 不混入 Message 表。它们属于下一阶段的 Execution / Trace。

## 6. Failure semantics

USER Message 在模型调用前落库。

如果模型或 Tool 中途失败：

- USER Message 保留。
- 不写伪造的完整 ASSISTANT Message。

这样数据库反映真实发生的事实。

失败原因和部分执行过程将在 Execution / Tool Trace 阶段记录。

## 7. Why MySQL, not Redis

Session / Message 是业务事实和审计数据，需要：

- 可恢复
- 可查询
- 可分页
- 可审计
- 可做统计

因此 MySQL 是 Source of Truth。

Redis 后续只承担：

- Hot Session Cache
- Runtime State
- Context Cache
- TTL

Redis 缓存丢失时，系统仍然应该能够从 MySQL 恢复会话事实。

## 8. Intentional boundary

本阶段完成“Conversation Transcript Persistence（对话记录持久化）”，但没有声称完成“Context Restore（上下文恢复）”。

AgentScope 当前仍使用：

```text
InMemoryAgentStateStore
```

所以 JVM 重启后：

- 历史消息仍可查询。
- Session 身份仍存在。
- 但模型运行时上下文不会自动从 MySQL 重建。

这是后续 Redis Session Cache / Context Restore 要解决的问题。

## 9. Verification

执行：

```powershell
git pull origin master
.\scripts\mvn.ps1 clean test
.\scripts\run-dashscope.ps1
```

Flyway 应执行：

```text
V2__create_session_message_tables.sql
```

数据库新增：

```text
af_session
af_message
```

发送一轮 Agent 请求后：

```powershell
Invoke-RestMethod "http://localhost:8080/api/v1/agents/default/sessions/session-persist-001/messages?userId=verify-user" |
  ConvertTo-Json -Depth 8
```

应至少看到：

```text
sequenceNo=1 role=USER
sequenceNo=2 role=ASSISTANT
```

重启 JVM 后再次 GET，消息仍然存在，即证明本阶段持久化闭环。
