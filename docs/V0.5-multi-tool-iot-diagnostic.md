# V0.5 — Multi-Tool IoT Diagnostic Agent

## 1. 阶段目标

V0.4 已完成 Tool Governance、Outbound HTTP Telemetry、Risk Policy、Durable Confirmation 和受控真实设备写操作验收。

V0.5 不继续扩写操作，也暂不引入 RAG / Workflow。目标是验证：

> Agent 能否为了完成一个 IoT 运维目标，自主选择并连续调用多个只读 Tool，再把多源观测组合为可解释的诊断结论。

现有 yudao 平台保持零修改。

## 2. Tool 组合

```text
query_device_status
query_device_properties
query_device_events
```

三者均为：

```text
readOnly = true
riskLevel = LOW
policyDecision = ALLOW
```

不会进入 HITL Confirmation。

专用 Agent：

```text
id = iot-diagnostic
```

默认只绑定以上三个只读 Tool，不绑定 `set_lure_lamp_state`。

## 3. yudao 复用接口

V0.5 只读复用：

```text
GET /admin-api/device/web/devices/{deviceId}
GET /admin-api/device/web/devices/{deviceId}/details
GET /admin-api/device/web/devices/{deviceId}/events/history?pageNo=1&pageSize=N
```

不修改 yudao Controller、Service、Mapper、MQTT、数据库模型或设备控制逻辑。

## 4. 租户安全边界

源码审计发现：

- `/devices/{deviceId}/details` 有显式 tenant-device relation 校验；
- `/properties/latest` 没有同等显式设备归属校验；
- `/events/history` 只有权限点，没有同等显式设备归属校验。

因此 AgentForge 采用旁路防御：

### 属性

```text
query_device_properties
  -> /details
  -> tenant ownership check
  -> 只提取 properties 最新值
```

不调用 `/properties/latest`。

### 事件

```text
query_device_events
  -> /details                  # ownership guard
  -> authorized
  -> /events/history
```

Guard 返回 FORBIDDEN / NOT_FOUND 时，history 请求不会发送。

## 5. Tool Schema

`query_device_properties`：

```json
{"deviceId":"373"}
```

`query_device_events`：

```json
{"deviceId":"373","limit":10}
```

`limit` 默认 10，范围 1..20。

LLM 不接触 Base URL、Token、tenant-id 或后端 path。

## 6. 数据最小化

属性结果只暴露：

```text
deviceId
deviceNickname
productId
observedAt
properties
  identifier -> name/value/observedAt/source/shadowStatus
source
```

事件结果只暴露：

```text
deviceId
total
count
events
  eventId/eventName/data/occurredAt
source
```

后端 JSON 字符串形式的属性/事件 payload 在 Adapter 层尽量还原为结构化对象。

## 7. Multi-Tool Runtime

当前 AgentScope Runtime 已支持：

```text
model
 -> tool A
 -> model
 -> tool B
 -> model
 -> final answer
```

每个 Tool Call 独立经过 Policy、Governance、boundedElastic 执行、SSE Trace 和 Durable Trace。

所以 V0.5 不增加固定 Workflow。工具选择继续由模型动态完成，Runtime 只负责确定性的执行与治理边界。

## 8. 验收

禁止使用“you must use xxx tool”类强制提示。

自然语言验收：

```text
检查设备 373 最近运行是否正常，并告诉我你的判断依据。
```

要求：

1. Qwen 自主选择工具；
2. 诊断请求一次 Execution 至少出现 2 个不同只读 Tool；
3. Tool Result 能进入下一轮模型上下文；
4. 每个 Tool Call / Result 有独立 SSE 和 Durable Trace；
5. LOW/read-only Tool 不产生 Confirmation；
6. 单个 Tool 失败不应强制整个 Execution 失败；
7. 最终回答区分“工具观测事实”和“基于事实的推断”；
8. yudao 仓库零修改。

## 9. 当前限制

`query_device_events` 一个 Tool 内包含两个只读 HTTP Hop：先 `/details` Guard，再 `/events/history`。

当前 `ToolTelemetryBuffer` 只保留最近一次 Outbound HTTP Telemetry。因此成功路径 Trace 主要反映 history 请求；如果 Guard 失败，则记录 Guard 请求。

后续如果需要完整展示单 Tool 内的多 HTTP Hop，可把 telemetry 从 latest-value 扩展成有界列表。本 Slice 不以此为阻塞项。
