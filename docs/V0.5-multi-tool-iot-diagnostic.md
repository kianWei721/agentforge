# V0.5 — Multi-tool IoT Diagnostic Agent

## Goal

V0.5 validates that one Agent can autonomously combine multiple low-risk read tools while preserving evidence boundaries.

Public examples use synthetic external IoT APIs only.

## Tools

```text
query_device_status
query_device_properties
query_device_events
```

A diagnostic Agent may bind these read-only tools while excluding write tools.

## Synthetic backend paths

```http
GET /api/iot/devices/{deviceId}
GET /api/iot/devices/{deviceId}/details
GET /api/iot/devices/{deviceId}/events/history?pageNo=1&pageSize=N
```

Credentials and tenant context are injected by the adapter, not supplied by the model.

## Evidence boundary

The final answer must distinguish:

```text
Observed fact
Model inference
Unknown
```

An empty event-history result means only that the queried feed returned no records. It must not be rewritten as “there were no alarms” unless the queried feed is explicitly an alarm feed.

Similarly, a saved property snapshot is not live telemetry unless its timestamp is sufficiently fresh.

## Acceptance focus

- autonomous selection of at least two distinct read-only tools;
- Tool policy remains `ALLOW`;
- no write tool is invoked;
- Tool Call / Result correlation is durable;
- final response does not upgrade stale or missing evidence into a confirmed root cause.
