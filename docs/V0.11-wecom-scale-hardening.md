# V0.11 — WeCom Channel at Ten Thousand Groups

## 1. 版本目标

V0.10 做出了按人、按群隔离的企业微信渠道。这一版回答的问题是：**上万个客户群同时在用时，它还成不成立。**

- 隔离在规模下仍然成立：一个群的回答和记忆里只出现这个群自己的内容；
- 记忆有界：再长的群聊，送进模型的上下文也有上限，而且对话内容不落本地磁盘；
- 过载时当场拒绝：按实测的回合耗时估算赶不上企业微信回复窗口的消息，在收到时就拒，不让用户等几分钟后看到"已过期"，群里连续追问也一样；
- Agent 内部缓存有界：不会随着服务过的群数一直涨。

## 2. 万群验证发现的问题

先用企业微信模拟器和确定性假模型跑了一万个群（见第 7 节），隔离本身没有问题：5 万个回答没有一个串群。暴露的是下面四个规模问题：

| 问题 | 后果 | 这一版的处理 |
|---|---|---|
| AgentScope 压缩前默认 flush + offload，把对话写到 `<user.dir>/.agentscope/workspace/<userId>/`；超过 8 万字符的工具结果也会写到工作区 | 客户对话落在应用机器的本地磁盘上，不受数据库权限、备份和清理策略管 | 全部关掉，见第 3 节 |
| 压缩默认只按消息条数触发（50 条），不看长度 | 几十条长消息就能让 prompt 无限变大 | 加 token 阈值和摘要长度上限 |
| 准入只看全局排队长度（64） | 量一大就拒，64 是万群并发时真正的瓶颈；而排进队的回合能不能在窗口内跑完，没人判断 | 改按截止时间准入，排队上限只当内存上限 |
| ReActAgent 的 `stateCache`、`permissionEngineCache` 按会话缓存，从不清理 | 实测每个会话约 7.3 KB，一万个群约 71 MB，并且只增不减 | 代际轮换 |

## 3. 记忆：有界，不落盘

构建 HarnessAgent 时：

- `disableSessionPersistence()`：会话状态已经在 state store（Redis）里，不再往工作区写一份会话文件；
- `disableToolResultEviction()`：不把大工具结果转存到工作区。渠道只放行 `search_knowledge`，检索结果本来就受检索预算限制；
- 压缩配置 `flushBeforeCompact(false)`、`offloadBeforeCompact(false)`：压缩前不把旧消息写盘；
- 压缩触发：消息数到 50 **或** 估算 token 到 12000，先到先算；保留最近 20 条原文，更早的压成一段中文摘要。摘要提示词要求不超过 800 字，模型不遵守时在输出端截断：压缩用的模型包了一层，超出部分丢掉并结束这次调用（压缩器只拼接文本块，读字节码确认）。

AgentScope 仍然需要一个工作区根目录，默认放在系统临时目录下的 `agentforge/agentscope-workspace`，可用 `AGENTFORGE_AGENT_WORKSPACE` 指定。测试断言跑完之后这个目录下一个文件都没有。

## 4. 准入：按截止时间，不按队列长度

企业微信从用户发消息起最多拉取 6 分钟回复，V0.10 已经把截止时间定为收到消息后 5 分 40 秒。这一版在**收到消息的那一刻**就估算：这条消息排队加上自己跑完，还赶不赶得上。

```text
一个回合预计耗时 = 真实回合耗时的滑动平均（EWMA，权重 0.2）
                  若正在跑的回合平均已经跑得更久，取它，但最多到平均值的 2 倍

剩余时间 ≤ 0                              → 拒绝
有空闲 worker，且本会话没有在跑或排队的回合 → 接受
    （空闲 = 在跑的回合数 + 已交给线程池、还没开始的会话数 < worker 数；
     会话自己排着的追问不算，它们在这个会话已占的 worker 上跑）
本会话已经在跑    → 前面的回合 = 本会话在跑的 1 个 + 本会话排队的
其他情况          → 前面的回合 = ceil((排队总数 + max(0, 在跑数 + 1 − worker 数)) / worker 数)
                                 + 本会话已经排上的回合（如果有）
预计完成 = (前面的回合 + 自己 1 个 + 余量 1 个) × 一个回合预计耗时
预计完成 > 剩余时间  →  当场拒绝，WOULD_MISS_DEADLINE
```

- **同一会话的回合在同一个 worker 上接着跑。** 一个回合跑完，这个 worker 直接取同一会话的下一条，不再排回全局队尾。否则群里的追问要把全局队列再等一遍，实际等待是估算的好几倍，接受之后照样过期。代价是一个群最多连续占一个 worker 4 个回合（1 个在跑、3 个排队）。
- **只从真实回合学。** 跑出回答（DONE）或跑满时限（TURN_TIMEOUT）的回合才计入平均。排队过期、被白名单拦下、模型秒回失败的回合只有几毫秒，计进去会把平均拉低：估算变乐观，接得更多，过期更多，平均又被拉得更低。
- **为什么要看正在跑的回合：** 滑动平均只从跑完的回合里学，模型突然变慢时会滞后。正在跑的回合已经跑了多久，是最早的信号。
- **为什么封顶 2 倍：** 一次几百毫秒的抖动乘上几百个排队回合，会一口气拒掉上千条本来赶得上的消息。实测不封顶时会过度拒绝。
- **余量一个回合：** 估算是平均值，离截止线最近的那几条最容易超时。
- **有空闲 worker 就接：** 这条消息马上就能开始，执行时本来就按剩余时间截断。要是估算偏高时连空闲都拒，就再没有回合跑完来纠正它，会一直拒下去，只能重启。
- **冷启动：** 还没有回合跑完时用配置的 `expected-turn-duration`（默认 15 秒），宁可估慢。第一个回合要建 agent、加载类，比平时慢。
- 用户看到的文案和"咨询的人比较多"一样；入站表记 `REJECTED`，错误码 `WOULD_MISS_DEADLINE`，和真正的内存上限 `OVERLOADED` 区分开。
- `max-pending-turns` 从 64 提到 1000，只防内存，不再决定接不接。

**容量怎么估：** 吞吐 ≈ worker 数 ÷ 单回合耗时。默认 4 个 worker、一个回合 15 秒，一个 5 分 40 秒的窗口里最多能答完约 4 × 340 ÷ 15 ≈ 90 条；留出一个回合的余量后，突发时大约第 84 条之后的消息会被当场拒绝。要答更多，加 worker；worker 数的上限是模型侧的并发和配额，不是这台机器。

**指标**（注册在 Micrometer 里）：

| 指标 | 说明 |
|---|---|
| `agentforge.wecom.admission{outcome}` | 每条消息的准入结果：`ACCEPTED`、`SESSION_BUSY`、`OVERLOADED`、`WOULD_MISS_DEADLINE`，以及路由阶段的拒绝码 |
| `agentforge.wecom.turn{outcome}` | 回合结局：`DONE` 或失败码（`TURN_TIMEOUT`、`EXPIRED_IN_QUEUE`、`MODEL_*` 等） |
| `agentforge.wecom.queue.wait` | 从准入到开始执行的排队时间 |
| `agentforge.wecom.turn.duration` | 回合执行时间 |

默认只暴露 `health,info`，因为 `/actuator` 不在身份过滤器的保护范围内（过滤器只管 `/api/v1`）。在内网或者 actuator 不对外的部署里，设 `AGENTFORGE_ACTUATOR_EXPOSURE=health,info,metrics` 后可以从 `/actuator/metrics/agentforge.wecom.admission` 等路径读取。要导出到 Prometheus 等监控系统需要再加对应的 Micrometer registry 依赖，这一版没有加。

`WOULD_MISS_DEADLINE` 持续上涨就是该加 worker 或换更快的模型；`TURN_TIMEOUT`、`EXPIRED_IN_QUEUE` 不为 0 说明估算偏乐观。

失败码里有模型网关的码，不由这边控制，所以 outcome 最多记 64 种取值，超出的或不像错误码的记成 `OTHER`；入站表里保留原始错误码。

## 5. 代际轮换

AgentScope 的两个按会话缓存是私有字段，没有淘汰接口。但每个回合开始时都会从 state store 重新加载会话状态，所以换一个新的 agent 实例不会丢任何东西。`AgentRuntimeManager` 因此按"代"管理 runtime：

- 一代跑满 `runtime-generation-turns`（默认 5000）个回合后，下一个回合新建一代；
- 旧一代不再接新回合，**正在跑的回合跑完后才关闭**；
- agent 定义版本变化时同样走这个流程，不会打断正在跑的回合；
- 设为 0 关闭轮换。

5000 个回合最多涉及 5000 个会话，按实测每会话 7.3 KB，一代缓存上限约 36 MB（轮换瞬间新旧两代并存）。

## 6. 配置

```yaml
agentforge:
  agent:
    runtime-generation-turns: 5000       # 0 = 不轮换
    memory:
      workspace: ""                      # 留空 = 系统临时目录；不会写入对话内容
      compaction-trigger-messages: 50
      compaction-trigger-tokens: 12000
      compaction-keep-messages: 20
      summary-max-chars: 800
  channel:
    wecom:
      max-concurrent-turns: 4            # worker 数，决定吞吐
      max-pending-turns: 1000            # 只是内存上限
      max-queued-per-session: 3
      expected-turn-duration: 15s        # 冷启动时的单回合耗时估计，不能超过 turn-timeout
      turn-timeout: 5m                   # 不能超过 5 分 40 秒的回复窗口
```

配置不合法（保留条数不小于触发条数、token 阈值过小等）启动失败。`turn-timeout` 原来只要求短于 6 分钟；落在 5 分 40 秒到 6 分钟之间时，跑满时限的回合会把平均耗时教成一个没有回合能被接受的值，现在启动时就拦下。

## 7. 测试分档与实测

**默认档**（每次构建都跑）：

| 测试 | 证明什么 |
|---|---|

| `WeComAdmissionTest` | 先逐条预热 8 个回合，再让消息按泊松分布到达 4 秒，约为 2 个 worker（模型 300 毫秒、窗口 4.5 秒）处理能力的 3 倍。两种到达方式：每群 1 条；每群连发 3 条。接受的全部按时答完，0 条排队过期、0 条超时，其余当场拒绝。本机一次：每群 1 条接受 50 / 拒绝 36，每群 3 条接受 48 / 拒绝 36。**限 2 核连跑 3 次**也都是 0 条迟到（每次接受 41–51 条） |
| `SessionTurnGateTest`（新增 7 个） | 赶不上截止时间的回合当场拒，压线的被余量拦下；正在跑的回合比平均慢时估算随之上调；追问在同一个 worker 上紧接着跑，不排到别的会话后面；正在跑的会话的追问只等自己的回合，新会话要等全局队列；有空闲 worker 时估算再高也接受；别的会话排着的追问不会把空闲 worker 算成被占；没真正跑的回合不改变平均 |
| `SummaryLengthLimitedModelTest` | 模型不守摘要长度时在 800 字处截断并结束调用；限内的摘要不变；不会截断在代理对中间 |
| `AgentRuntimeManagerTest` | 跑满即换代并关闭旧代；旧代等正在跑的回合结束才关；版本变化同样等；启动就失败的回合也释放，旧代照样能关；0 不换代 |
| `WeComChannelPropertiesTest` | `turn-timeout` 超过 5 分 40 秒的回复窗口时启动失败 |

**规模档**（默认不跑）：

```bash
mvn -pl agentforge-infrastructure test -Dagentforge.scale=true -Dtest=WeComGroupIsolationScaleTest
```

一万个群的实测（假模型，单机）：

| 场景 | 结果 |
|---|---|
| 两轮提问 + 每群连发 3 条，共 5 万个回合 | 0 串群、0 历史错误、0 未完成；换成按文件序列化的 state store（模拟 Redis 的序列化）结果相同 |
| 每 2000 个回合换一代 | 换了 25 代，0 串群；当前代的缓存最多是 2000 个会话加 1 个默认槽（agent 构造时建的），两次实测 2001 / 2000、673 / 672 条，取决于结束时这一代跑了多少回合；不轮换时是 10001 / 10000 |
| 缓存占用 | 两个缓存共 71–72 MB，每会话 7.3–7.4 KB（两次实测） |
| 出厂配置下一万个群同时各发一条（模型 300 毫秒） | 1,008 条按时答完，8,992 条因 1000 的内存上限当场拒绝；0 条排队过期、0 条超时 |

最后一行里模型是假的、很快，所以先触顶的是内存上限；换成 15 秒一个回合的真实模型，先起作用的会是截止时间准入（约 84 条，见第 4 节）。

## 8. 已知限制与没做的事

- **单实例。** 串行门、耗时估算、流缓存都在 JVM 里；多实例要按会话路由，或者改成共享锁和共享缓存。
- **HTTP 入口在换代边界上的同会话并发。** AgentScope 的会话串行锁是每个 agent 实例一把，同一会话的两个 HTTP 请求可能分别落在新旧两代上同时跑。V0.10 已经记录 HTTP 入口的同会话并发没修，换代多了一种情况。企业微信渠道由串行门保证不受影响。
- **估算不是保证。** 它是平均值加一个回合的余量：模型突然慢到平均值的 2 倍以上，或者进程内的开销和回合本身差不多大时，已接受的回合仍可能超时。后一种在两核机器上跑 100 毫秒的假模型时就会出现，所以准入测试用 300 毫秒的回合。被拒的消息不会稍后补答。
- **模型失败不计入平均。** 模型如果持续慢速失败（比如每次 30 秒后报错），平均学不到这个慢，只能靠"正在跑的回合"那一项上调，最多到 2 倍。
- **一个群可以连续占住一个 worker。** 最多 4 个回合，由每会话排队上限 3 决定。
- **缓存占用是用假模型、短回答测的。** 带工具调用的真实会话状态更大，轮换阈值要按真实指标再调。
- **压缩摘要用的是 agent 自己的模型**：和 Agent 一样直连 DashScope，没走模型网关，也没有单独指定便宜的路由。
- 没做：群绑定从配置迁到数据库表（需要新表，待确认）；意图路由（下个版本）。
