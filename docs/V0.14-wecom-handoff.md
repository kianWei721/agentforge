# V0.14 — 转人工闭环（企业微信渠道）

## 1. 版本目标

V0.12 的转人工只做到"登记"：入站表写成 `HANDOFF`，回一句"已登记，请直接联系群里的客服同事。"，没人被通知，没人认领，也没有处理结果。这一版补成闭环：

```text
转人工（短语或模型判定）
  → 同一事务：入站行 HANDOFF + 开单（或并入这个会话已开的单）
  → 员工群机器人推送（可选，单线程定时合并推送）
  → 客服经 staff 接口认领、结单（处理 / 无需处理 / 误触发）
  → 工单表、入站表、网关流水按 inbound id / correlation id 串起来
```

同时修掉 V0.12 的已知问题：短语段对否定句（"不用转人工"）会误触发。有了通知以后，误触发会直接打扰员工，代价变高了。

## 2. 关键取舍

| 问题 | 选择 | 放弃的做法 |
|---|---|---|
| 工单放哪 | 新表 `af_channel_handoff`（V13） | 入站表加列：入站表一条消息一行，工单是一个会话的诉求，有自己的认领、结单生命周期，混在一起要加十几列，大部分行永远为空 |
| 粒度 | 每个会话同时只有一张未结工单，后续转人工并入（`message_count + 1`） | 一条消息一张单：客户连发三次"转人工"就是三张单，万群突发时员工群被刷屏 |
| 怎么保证一个会话只有一张未结单 | `active_key` 未结时等于会话键、结单置空，加唯一键；照搬工具确认表的写法 | 内存里的单群冷却：重启就丢，多实例不成立 |
| 通知可靠性 | 工单行本身就是 outbox（`notify_*` 列），定时任务扫描推送；入站行和工单同事务 | 内存队列：重启丢消息 |
| 限频 | 每次 tick 最多发 1 条合并消息，最多列 10 单，其余写"另有 N 条"；默认 5 秒一次，即每分钟不超过 12 条，低于企业微信每个机器人 20 条/分钟 | 令牌桶：效果一样，多一个组件 |
| 回写方式 | staff 专用接口 | 在员工群里回复关键词：要再接收一个群的消息，过度设计 |
| 没配 webhook | 照样开单，接口可查；给客户的文案保持"已登记" | 不开单：闭环就断在通知上 |

不引入新依赖：JDK `HttpClient`、JDK `ScheduledExecutorService`、已有的 spring-jdbc 事务。

## 3. 数据模型

`V13__create_channel_handoff_table.sql`，回滚语句在文件头（`DROP TABLE af_channel_handoff;`，入站表不动）。

- `active_key`：未结时是会话键，结单置 NULL；唯一键保证一个会话最多一张未结单。会话键和 chatId 区分大小写，所以用 `utf8mb4_bin`。
- `first_inbound_id` 唯一，`last_inbound_id` 指向最近一条；`message_count` 是并入的消息数。
- `excerpt`：消息摘录。11–19 位的数字串（半角或全角，允许用单个空格或连字符分组，如"138 1234 5678""6222-0212-..."，最后一位可以是 X）视为手机号、身份证号、银行卡号，只留首 3 位和末 4 位，再截到 `excerpt-chars`（默认 120）个字符；`excerpt-chars: 0` 时不存也不推。
- `status`：`PENDING → CLAIMED → RESOLVED`，`PENDING` 也可以直接结单。
- `resolution`：`HANDLED / NO_ACTION / FALSE_TRIGGER`。`FALSE_TRIGGER` 的占比就是误转人工率。
- `notify_status`：`PENDING / SENT / FAILED / DISABLED / CANCELLED`。`DISABLED` 是开单时没配 webhook；`CANCELLED` 是通知发出前已经被认领或结单，不再让员工群"待认领"一张已有人处理的单。

开单或并入是一条 `INSERT ... ON DUPLICATE KEY UPDATE message_count = message_count + 1, ...`，再按 `active_key` 读回工单 id：和新生成的 id 不同就是并入。最初写的是"先 INSERT，撞键再 UPDATE"，审查指出 InnoDB 下会死锁：撞键的 INSERT 在重复的索引记录上持有共享锁，两个并入方（或并入方和结单）随后的 UPDATE 都要升级成排他锁，互相等待。`ON DUPLICATE KEY UPDATE` 撞键时直接拿排他锁。另外，入站行加开单的整个事务在锁冲突（死锁被选为牺牲者、锁等待超时）时再执行一次；整个事务已回滚，重跑不会重复记录。整个过程在记录入站消息的那个事务里。

## 4. 两个入口

| 入口 | 位置 | 怎么写 |
|---|---|---|
| 短语段转人工 | 回调线程 | `insertHandoff(入站行, 开单)`：一个事务；重复投递返回空，不开第二张单、不重复计数 |
| 模型段转人工 | worker | `completeAsHandoff(入站 id, 开单)`：入站行改 `HANDOFF` 和开单一个事务；失败时入站行保持 `RECEIVED`，按状态和时间能查出来，客户收到的是不承诺的原文案（见下） |

客户收到的文案：配了 webhook 且工单已落库时是"已转给客服同事，他们会在群里回复你。"（"转给"成立，不承诺时间）；没配 webhook，或模型段开单失败时，是意图自己的"已登记，请直接联系群里的客服同事。"——没有工单就没人会被通知，不能说已转达。短语段开单失败时入站行一起回滚，回调返回错误，企业微信重投后重来。

## 5. 通知

`HandoffNotificationDispatcher`，单个守护线程，`scheduleWithFixedDelay`（webhook 慢时拉长间隔，而不是之后连发）：

1. 取到期的待推送工单（`notify_status = PENDING` 且到了重试时间），最多 200 张，最老的在前。
2. 拼一条 text 消息：最多列 `max-items-per-message`（默认 10）张，其余写"另有 N 条，见待办列表"；总长控制在 2000 字节以内（企业微信上限 2048）。
3. 发送结果：
   - `errcode = 0`：这批全部标 `SENT`，包括只计数没列出的；
   - `errcode = 45009`（限频）：整体暂停 60 秒，不算一次失败；
   - 其他失败：每张单 `attempts + 1`，按 10 秒 / 30 秒 / 2 分 / 5 分退避，到 `max-attempts`（默认 5）标 `FAILED`。工单本身仍是 `PENDING`，接口照样能查到。
4. 每次 tick 顺带统计未结工单数，作为指标。

企业微信对大多数失败也返回 HTTP 200，原因写在 `errcode` 里，所以只认 `errcode = 0`。webhook 地址里带机器人的 key：只从环境变量注入，启动时校验必须是 `https://qyapi.weixin.qq.com/...`（客户原文会发到这个地址），日志和失败原因里只写 errcode 或异常类型，不写地址。

消息样例：

```text
【转人工】待认领 2 条
1) 群 acme（客户 C001）｜发起人 zhangsan｜短语｜10-26 14:03
   "我要投诉你们的会计"
   工单 3f2a9c1e-...
2) 单聊 u-1001｜发起人 lisi｜模型 0.92｜10-26 14:03｜共 3 条
   "……"
   工单 8b1d...
认领：POST /api/v1/channel-handoffs/{id}/claim；结单：POST /api/v1/channel-handoffs/{id}/resolve
```

**至少送达一次**：webhook 已经收下、还没来得及标 `SENT` 时进程崩溃，重启后会再发一次。每条都带工单 id，员工能认出重复。

## 6. 接口

前缀 `/api/v1/channel-handoffs`，只有企业微信渠道开启时注册，全部要求 staff 身份（`AccessDeniedException.requireStaff`）。认领人、结单人一律取服务端解析的身份，请求体里不能指定。

| 方法与路径 | 说明 | 错误 |
|---|---|---|
| `GET /?status=PENDING&createdAfter=&limit=50` | 按创建时间升序（最老的先处理），`limit` 1–100 | 400 |
| `GET /{id}` | 详情 | 404 |
| `POST /{id}/claim` | 只能从 `PENDING` 认领 | 409（返回当前状态和认领人） |
| `POST /{id}/resolve` | `{"resolution": "HANDLED", "note": "..."}`，备注最多 500 字；`PENDING` 或自己认领的才能结 | 409 |

返回内容不带原始 chatId 和会话键，群用运维配置的名字（`wecom-group:<name>`）显示。

## 7. 否定词守卫

短语按分句匹配：消息先按标点、换行、全角空格和"～"（聊天里常代替逗号）切开；关键词**前面 4 个字符以内**出现 `不用 / 不要 / 不是 / 不需要 / 无需 / 别 / 没有 / 暂时不` 之一，这处命中就不算，消息交给模型段（模型段关着就落到默认意图 `answer`）。判断前先去掉含这些字但不是否定的词：是不是、要不要、用不用、需不需要、特别、区别、别人、别的、级别、个别、分别、类别、告别。

- "不行，我要投诉"：否定词在另一个分句，照常转人工。
- "我要投诉你们客服特别慢""是不是可以转人工""不要机器人了（换行）转人工"：照常转人工。第一版是"分句里任何位置有否定词就不算"，审查指出这几类都会被误判成否定，改成了窗口加复合词剔除，并补了回归测试。
- 不按普通空格切：短语里可能带空格（"write code"）。
- 切分用一个字符类，回调线程上不会出现正则回溯。

效果：

| 数据 | 结果 |
|---|---|
| 原标注集 104 条 | 短语段误触发从 6 条（全是否定句）降到 0；显式转人工全部照常命中 |
| 新写的 16 条否定句样本（`intent-negation-holdout.jsonl`），在写守卫之前标注，不参与调规则 | 15 / 16 正确（改成窗口规则后重跑，结果不变）；漏的是 n08 "我不想投诉，只想知道流程"："不想"不在否定词表里。按约定不为这条样本补词，列为已知局限 |
| 审查发现的 8 条"看起来像否定、其实要人工"的句子 | 写成回归测试（`IntentRouterTest`），不算 held-out：它们是在看到第一版规则之后才写的 |

## 8. 配置

```yaml
agentforge:
  channel:
    wecom:
      handoff:
        webhook-url: ${AGENTFORGE_WECOM_HANDOFF_WEBHOOK:}     # 空：照样开单，不通知
        mention-userids: ${AGENTFORGE_WECOM_HANDOFF_MENTION:} # 要 @ 的企业微信 userid
        reply-when-notified: 已转给客服同事，他们会在群里回复你。
        excerpt-chars: 120        # 0：不存摘录
        notify-interval: 5s       # 至少 3 秒
        max-items-per-message: 10 # 1–20
        max-attempts: 5           # 1–10
        webhook-timeout: 4s       # 必须短于 notify-interval
        zone: Asia/Shanghai       # 通知里时间的时区
```

## 9. 指标与追溯

| 指标 | 含义 |
|---|---|
| `agentforge.wecom.handoff.opened{result=NEW\|MERGED, source}` | 和 `agentforge.wecom.intent{intent=handoff}` 对得上 |
| `agentforge.wecom.handoff.notify{outcome=SENT\|RETRY\|FAILED\|RATE_LIMITED}` | 每次推送一个 |
| `agentforge.wecom.handoff.notify.delay` | 开单到推送成功 |
| `agentforge.wecom.handoff.open{status=PENDING\|CLAIMED}` | 未结工单数，每次 tick 刷新（只有配了 webhook 才有） |
| `agentforge.wecom.handoff.claim.wait`、`.resolve.duration{resolution}` | 等待认领、处理时长；`resolution=FALSE_TRIGGER` 是误转人工 |

追溯链：工单的 `first_inbound_id` / `last_inbound_id` → 入站行（意图、来源、置信度、`intent_request_id`）→ 网关流水（correlation id `wecom-<入站 id>`）。

## 11. 已知局限

- **没有接真实员工群**：通知只用假 webhook 测过，没往真实企业微信群发过。
- **接口层没有自动化测试**：`agentforge-app` 模块一直没有测试，`ChannelHandoffController` 的鉴权（非 staff 返回 403）靠代码审查和 `requireStaff` 的既有测试。
- **结单不会通知客户**：智能机器人只能在流式回复里说话，没法主动推到客户群；客服要自己在群里回复。
- **一张单长期不结，这个会话后续的转人工都只并入、不再推送**。P0 只能靠列表巡检；超时未认领提醒是 P1，加一个可空列 `reminded_at` 即可。
- **认领后只有认领人能结单**，没有管理员改派或强制结单；认领人离开时这张单会一直挂着。改派（`/release`、`/reassign`）是 P1。
- **摘录脱敏只认长数字**，姓名、地址、邮箱不处理；员工群的成员范围可能比客户群里的客服更大，不需要时把 `excerpt-chars` 设为 0。
- **单实例**：推送扫描在多实例下会重复发送；多实例时改成 `SELECT ... FOR UPDATE SKIP LOCKED`。认领、结单本来就是条件更新，多实例下也成立。
- **并发并入只在 H2 上测过**：`ON DUPLICATE KEY UPDATE` 避免死锁是按 InnoDB 的加锁规则推出来的，没有在真实 MySQL 上做并发复现。
- **否定词守卫是启发式**："我不想投诉"这类不在词表里的否定照样会转人工；反问句"为什么不能转人工？"照常转人工，这是对的。
