# V0.6.3 — Retrieval Quality / Relevance Gate

## 1. 背景

V0.6.2 已完成真实 Hybrid Retrieval 验收：

```text
中文 Query
-> qwen3.7-text-embedding
-> Elasticsearch 7.17 exact cosine
   + BM25
-> Java RRF
-> 英文 Knowledge
```

真实 Agent 验收同时暴露了一个新的检索质量问题。

知识库当时只有一篇离线排查 TEST 文档，但 Agent 连续检索：

```text
设备离线排查
shadowStatus CONFLICT
SignalStrength=0
PeripheralStatus
```

四个查询都返回同一篇离线排查文档。

这不是 RRF 算错，而是向量检索的固有行为：最近邻搜索会返回“最接近的候选”，但“最接近”不等于“足以回答”。

因此 V0.6.3 第一阶段不先做 Reranker，而先回答更基础的问题：

```text
这个候选到底该不该返回？
```

## 2. Slice 1 目标

- Relevance Gate（相关性门槛）
- No-answer（无相关知识）语义
- 可观测的 matchType / vectorSimilarity
- 真实语料校准脚本

暂不实现 Cross-Encoder Reranker、LLM Judge、Query Rewrite、Runtime Retrieval Budget；这些留在后续 Slice。

## 3. Gate 规则

Hybrid 仍先执行 BM25 + Vector + RRF，之后增加 Gate：

```text
candidate 来自 lexical channel
    -> 保留

candidate 仅来自 vector channel
    -> normalized cosine similarity >= minVectorSimilarity
       才保留
```

默认：

```text
relevanceGateEnabled = true
minVectorSimilarity  = 0.60
```

环境变量：

```text
AGENTFORGE_KNOWLEDGE_RELEVANCE_GATE_ENABLED
AGENTFORGE_KNOWLEDGE_MIN_VECTOR_SIMILARITY
```

这是 V1 策略。它优先解决“小知识库下任意 Query 都被 nearest-neighbor 强行返回”的问题，不声称已经解决所有语义相关性判断。

## 4. Elasticsearch score 归一化

Gate 不直接比较 Elasticsearch 原始 `_score`。

ES 7.17 当前使用 `cosineSimilarity(params.query_vector, 'embedding') + 1.0`，因此 `cosine = _score - 1`。

ES 8+ indexed cosine 的搜索分数也会先归一化回 cosine，再进入同一个 Gate。

最终 Gate 比较的 `vectorSimilarity` 范围为 `[-1, 1]`。

## 5. Search 结果语义

Hybrid mode：`HYBRID_ES_RRF_GATE_V1`。

Hit 新增：

```text
matchType = LEXICAL | VECTOR | HYBRID
vectorSimilarity = normalized cosine similarity
```

`score` 仍是 RRF fusion score，不是 cosine similarity、概率或置信度。

当全部候选被 Gate 过滤后：

```json
{
  "count": 0,
  "noAnswer": true,
  "noAnswerReason": "NO_RELEVANT_KNOWLEDGE_RETURNED",
  "hits": []
}
```

`search_knowledge` Tool 同样返回 no-answer 机器语义。

## 9. Slice 1A 实验结论：单 cosine threshold 不可行

真实 qwen3.7-text-embedding / ES 7.17 校准得到：

```text
positive offline procedure     0.4863
negative shadow CONFLICT       0.3064
negative SignalStrength=0      0.5643
negative PeripheralStatus      0.5008
```

因此不存在一个全局 cosine threshold 能同时做到：

```text
保留 positive  -> threshold <= 0.4863
拒绝全部 negative -> threshold > 0.5643
```

结论：Embedding similarity 继续用于 Candidate Generation 与可观测性，但不能单独承担 Answerability Gate。

## 10. Slice 1B：qwen3-rerank + NO_ANSWER_SENTINEL

候选链路升级为：

```text
BM25 + Vector
      ↓
RRF Candidate Top-N
      ↓
real candidates + synthetic NO_ANSWER_SENTINEL
      ↓
qwen3-rerank
      ↓
real candidates ranked before sentinel -> return
sentinel first -> noAnswer
candidates ranked below sentinel -> discard
```

`NO_ANSWER_SENTINEL` 仅存在于单次 Rerank 请求，不写入 MySQL、不写入 Elasticsearch、不能生成 Citation。

真实 API 实验中，4 个 Case 均正确排序：离线排查由真实离线文档 Rank 1；CONFLICT、SignalStrength、PeripheralStatus 三个当前知识库不支持的问题均由 NO_ANSWER Rank 1。

Reranker 启用后 Retriever mode：

```text
HYBRID_ES_RRF_RERANK_V1
```

Hit 额外暴露：

```text
rerankScore
```

`score` 仍是 RRF score；`vectorSimilarity` 仍是 embedding cosine；`rerankScore` 是当前 rerank 请求内的相关性排序分数。三者语义不得混用。

独立配置：

```text
AGENTFORGE_KNOWLEDGE_RERANK_ENABLED=true
AGENTFORGE_KNOWLEDGE_RERANK_BASE_URL=https://<workspace>.cn-beijing.maas.aliyuncs.com/compatible-api/v1
AGENTFORGE_KNOWLEDGE_RERANK_API_KEY=<secret>
AGENTFORGE_KNOWLEDGE_RERANK_MODEL=qwen3-rerank
AGENTFORGE_KNOWLEDGE_RERANK_CANDIDATE_LIMIT=8
```

Rerank API Key 与 LLM / Embedding Credential 独立，不应复用或打印。

启用脚本：

```powershell
.\scripts\configure-rerank.ps1
```

启用后不需要重建 Elasticsearch 索引，只需重启 AgentForge，再运行：

```powershell
.\scripts\evaluate-rag-v063.ps1
```

期望：Positive 命中真实英文知识；三个 Negative 均 `count=0 / noAnswer=true`。

## 11. Slice 1B 真实集成结论：Sentinel Admission 失败

手工多候选实验中，`qwen3-rerank + NO_ANSWER_SENTINEL` 曾得到 4/4 正确排序；但接入 AgentForge 后，真实单候选场景中 Positive 与三个 Negative 都被 Sentinel 排到 Rank 1。

进一步诊断确认每个 Query 都有 1 个真实 Candidate，问题不是 Elasticsearch Recall、RRF 或旧 cosine gate。真实 Candidate 的 rerank score 也无法形成可用的全局 Admission 阈值：

```text
positive offline        0.3580
negative CONFLICT       0.3997
negative SignalStrength 0.4570
negative Peripheral     0.4068
```

因此：

```text
qwen3-rerank = Candidate Ranking
qwen3-rerank != deterministic Answerability / No-answer Classifier
```

Synthetic NO_ANSWER_SENTINEL 不再参与最终 Admission 决策。

## 12. Slice 1C：Explicit Answerability Judge

使用现有 `qwen3.8-flash` 做独立 Answerability Judge。真实 API 评测的同一组 4 Case 全部通过：

```text
offline procedure        -> supported=true  / DIRECT_ANSWER
shadowStatus CONFLICT    -> supported=false / MISSING_REQUIRED_SEMANTICS
SignalStrength=0         -> supported=false / TOPIC_ONLY
PeripheralStatus         -> supported=false / MISSING_REQUIRED_SEMANTICS
```

最终 Pipeline：

```text
BM25 + Vector
      ↓
RRF Candidate Generation
      ↓
qwen3-rerank
Candidate Ordering only
      ↓
qwen3.8-flash
KnowledgeAnswerabilityJudge
      ↓
SUPPORTED   -> return hit + Citation
UNSUPPORTED -> filter hit
all unsupported -> noAnswer=true
```

完整模式：`HYBRID_ES_RRF_RERANK_JUDGE_V1`。

Answerability 默认复用现有 DashScope LLM 凭据，可通过以下配置启用：

```text
AGENTFORGE_KNOWLEDGE_ANSWERABILITY_ENABLED=true
AGENTFORGE_KNOWLEDGE_ANSWERABILITY_MODEL=qwen3.8-flash
AGENTFORGE_KNOWLEDGE_ANSWERABILITY_CANDIDATE_LIMIT=8
```

配置脚本：

```powershell
.\scripts\configure-answerability.ps1
```

该改动不涉及 MySQL Schema、Knowledge Chunk、Embedding 维度或 Elasticsearch Mapping，因此启用后无需 rebuild ES，只需要重启 AgentForge。

验收：

```powershell
.\scripts\evaluate-rag-v063.ps1
```

期望 Positive 返回英文离线知识；三个 Negative 均 `count=0 / noAnswer=true`，并通过 `answerabilityDiagnostics` 暴露 `supported / reasonCode`。

## 13. Slice 2：Retrieval Budget

Slice 1 已解决“召回到的候选能否回答 Query”的质量问题。Slice 2 处理另一个真实 Agent 问题：模型可能在一次诊断中连续多次调用 `search_knowledge`，导致 Embedding、Elasticsearch、Reranker 与 Answerability Judge 成本级联放大。

第一版采用确定性的 Runtime Budget，而不是只依赖 Prompt：

```text
scope = one Agent execution
target tool = search_knowledge
default limit = 3

call 1..3 -> ALLOW
call 4+   -> BLOCK before delegate.execute()
```

Budget 与 Query 参数无关，因此不同改写、不同关键词、不同 `topK` 都共享同一个 Execution 总额度。

策略顺序：

```text
Tool Policy
   ↓
Repeated-call Governance
   ↓
Retrieval Budget
   ↓
search_knowledge delegate
   ↓
Embedding -> ES -> Reranker -> Answerability Judge
```

如果 Policy 或既有 Governance 已经提前阻断调用，则不消耗 Retrieval Budget。Budget 自身阻断返回不可重试错误 `RETRIEVAL_BUDGET_EXHAUSTED`，并明确告诉模型不要继续调用 `search_knowledge`。

Trace 新增：

```text
retrieval_budget_decision = ALLOW | BLOCK | SKIP
retrieval_budget_reason
retrieval_budget_limit
retrieval_budget_used
retrieval_budget_remaining
```

数据库迁移：`V9__add_retrieval_budget_trace_columns.sql`。

配置：

```text
AGENTFORGE_RETRIEVAL_BUDGET_ENABLED=true
AGENTFORGE_RETRIEVAL_BUDGET_MAX_CALLS_PER_EXECUTION=3
```

该 Budget 每次 `AgentScopeHarnessRuntime.stream()` 创建新的 State，因此不同 Execution 之间完全隔离；同一 Session 的下一轮对话也会得到新的预算。

第一版只做硬上限，不做语义重复 Query 判定。后续只有在真实 Trace 证明“3 次以内仍存在大量同义检索浪费”时，才考虑 Query similarity / intent dedup，避免过度设计。

## 14. Slice 3：Query Rewrite + Expanded Evaluation

Slice 3 不继续增加新的 Ranking / Admission 模型，而是解决 Query 表达与回归测试覆盖面问题。

Query Rewrite 的职责边界：

```text
Original Query
   ↓
KnowledgeQueryRewriter
   ↓
Retrieval Query
   ↓
Embedding + BM25 + Vector + RRF

Original Query
   ├─> qwen3-rerank
   └─> qwen3.8-flash Answerability Judge
```

即：Rewrite 只服务 Candidate Recall，不允许替代用户原始问题进入 Answerability 判断。

第一版使用现有 `qwen3.8-flash`，`temperature=0 / enable_thinking=false / strict json_schema`。Prompt 约束：不得回答问题、不得添加原 Query 中不存在的故障步骤/原因/字段含义，必须逐字保留技术标识符、错误码、数值和操作符；允许删除口语填充词，并为相同概念补充简洁英文同义表达以帮助跨语言检索。

完整模式：

```text
HYBRID_ES_RRF_REWRITE_RERANK_JUDGE_V1
```

Rewrite Provider 属于 Recall 优化而非安全准入，因此失败策略是：

```text
rewrite provider failure
   -> FALLBACK_ORIGINAL
   -> original query continues to Embedding / ES
   -> Reranker / Judge still execute normally
```

这与 Answerability Judge 的 fail-closed 语义不同。

配置：

```text
AGENTFORGE_KNOWLEDGE_QUERY_REWRITE_ENABLED=true
AGENTFORGE_KNOWLEDGE_QUERY_REWRITE_MODEL=qwen3.8-flash
AGENTFORGE_KNOWLEDGE_QUERY_REWRITE_MAX_QUERY_CHARS=512
```

默认复用现有 `DASHSCOPE_API_KEY / DASHSCOPE_BASE_URL`，也支持独立覆盖 Query Rewrite 的 endpoint / credential。
